# Password Hashing and User Model

## Когда тема нужна
Как только в сервисе появляется user login, пароль нельзя хранить как обычную строку.

Это не stylistic preference. Это базовое требование безопасности.

Если пароль хранится как plain text, компрометация базы сразу превращается в компрометацию пользователей.

## Как мыслить правильно
Полезная модель такая:
1. пользователь присылает raw password;
2. backend превращает её в hash;
3. в базе хранится не пароль, а результат hashing + salt;
4. при логине пароль хэшируется тем же способом и сравнивается с сохранённым значением.

То есть backend никогда не должен нуждаться в восстановлении исходного пароля.

## Почему plain text и "просто sha256" — плохая идея
Plain text плох по очевидной причине: пароль сразу читаем.

`sha256(password)` тоже плохая идея, потому что:
- без salt одинаковые пароли дают одинаковый результат;
- быстрые hash-функции удобны атакующему для brute force;
- у тебя нет нормальной истории параметров hash policy.

На практическом уровне нужен хотя бы salted slow hash.

## Что здесь считать достаточным минимумом
Для учебного backend-блока достаточно понимать:
- у пользователя есть `password_hash` и `password_salt`;
- registration создаёт эти значения;
- login проверяет пароль через `verify_password()`;
- raw password не хранится в модели и не возвращается в API.

## User model — это не только таблица
User model обычно быстро обрастает полями:
- `email`;
- `password_hash`;
- `password_salt`;
- `role`;
- `is_active`.

Полезно сразу держать их как часть явного контракта, а не как случайный набор колонок.

## Где должна жить проверка пароля
Хорошая граница такая:
- hashing helper знает, как строить hash;
- service знает, когда вызывать helper;
- route не должен сам вручную сравнивать строки паролей.

## Типичные ошибки
- хранить raw password в базе или в возвращаемом payload;
- использовать одну и ту же соль для всех пользователей;
- зашивать проверку пароля прямо в route;
- смешивать user creation и auth verification в один нечитаемый кусок кода.

## Что нужно понять перед практикой
Перед `practice.py` должно быть ясно:
1. почему raw password не должна храниться;
2. зачем нужен salt;
3. почему registration и login должны работать через helpers и service layer, а не через прямые сравнения строк.
