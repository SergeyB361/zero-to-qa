# Partial Update and Soft Delete

## Когда тема нужна
В реальном backend изменение сущности редко выглядит как полный overwrite объекта.

Обычно клиент хочет:
- поменять одно или два поля через `PATCH`;
- пометить запись удалённой, но не терять её физически;
- сохранить возможность аудита и восстановления.

Отсюда и две практические темы: partial update и soft delete.

## Почему `PATCH` полезнее, чем бездумный `PUT`
`PATCH` нужен, когда клиент присылает только изменившиеся поля.

Это важно, потому что:
- клиенту не нужно знать весь текущий объект;
- снижается риск случайно перезаписать поля пустыми значениями;
- API-контракт лучше отражает реальные изменения.

## Как думать про partial update
Полезная модель такая:
1. есть update-schema с optional полями;
2. backend берёт только реально переданные значения;
3. service применяет изменения к существующей сущности;
4. ответ показывает уже обновлённое состояние.

В `Pydantic` это обычно читается через `exclude_unset=True`.

## Что такое soft delete на практике
Soft delete — это не физическое удаление строки, а изменение её статуса:
- `is_deleted = true`
- или `deleted_at = timestamp`

Это полезно, потому что:
- запись остаётся для аудита;
- её можно восстановить;
- связанные данные не ломаются так резко, как при hard delete.

## Но soft delete не бесплатный
Если у тебя есть soft delete, то backend должен явно решить:
- показываем ли такие записи в list endpoint;
- возвращаем ли их по `GET /resource/{id}`;
- как отличаем "не найдено" от "удалено".

На этом уровне нормальный контракт — скрывать soft-deleted записи из обычного чтения.

## Где должна жить логика
- router принимает `PATCH` payload и delete request;
- service решает, как применить partial update и soft delete;
- repository/storage сохраняет результат.

Если route сам вручную меняет поля сущности, слой service быстро теряет смысл.

## Типичные ошибки
- `PATCH` перезаписывает поля значением `None`, хотя клиент их не присылал;
- soft delete есть, но list endpoint всё равно показывает удалённые записи;
- delete route физически удаляет запись, хотя система ожидала audit-friendly поведение;
- бизнес-правила вокруг delete/update размазаны по route.

## Что нужно понять перед практикой
Перед `practice.py` должно быть ясно:
1. почему `PATCH` опирается только на переданные поля;
2. чем soft delete отличается от hard delete;
3. почему скрытие deleted records должно быть частью контракта сервиса.
