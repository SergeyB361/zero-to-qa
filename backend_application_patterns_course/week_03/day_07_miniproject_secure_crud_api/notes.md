# Mini-Project — Secure CRUD API

## Зачем этот mini-project
Теперь backend уже умеет:
- быть разложенным по слоям;
- работать с data layer;
- строить auth context;
- проверять роли;
- делать list/update/delete контракты более взрослыми.

Эту неделю нужно собрать в один API, который уже выглядит не как упражнение на один endpoint, а как маленький защищённый сервис.

## Что здесь считается хорошим результатом
Хороший результат — это сервис, где видно:
- auth dependency;
- role-based доступ;
- нормальный CRUD flow;
- partial update;
- soft delete;
- единый стиль ошибок.

То есть mini-project должен показать, что ты умеешь строить не только happy path, но и контракт доступа.

## Что здесь особенно важно
На этом этапе сервис уже не должен быть "полностью открытым".

Нормальный минимальный режим такой:
- list/read доступны валидному actor;
- create/update/delete доступны только повышенной роли;
- delete — soft delete;
- удалённые записи исчезают из обычного чтения.

## Как проверять себя
Перед тем как считать mini-project завершённым, полезно убедиться:
1. без API key сервис отдаёт `401`;
2. viewer не может создавать и удалять сущности;
3. manager/admin может создавать и изменять;
4. после soft delete сущность исчезает из `GET /items` и `GET /items/{id}`;
5. контракты `401/403/404` не перепутаны.
