# Auth Basics: Tokens and Headers

## Когда тема нужна
Как только backend перестаёт быть полностью публичным, появляется минимальный access layer:
- service token для internal API;
- `Authorization: Bearer ...` для пользователя;
- `X-API-Key` для административных операций;
- actor context, который нужен сервису для аудита и прав.

На этом уровне не нужен полноценный OAuth. Но нужна понятная модель: как request превращается в auth context.

## Как мыслить правильно
На junior/junior+ уровне полезно думать так:
1. клиент приносит credential в header;
2. dependency валидирует credential;
3. dependency превращает его в actor context;
4. route и service получают уже нормализованный результат.

Это важно, потому что route должен работать не с сырым header, а с уже проверенным контекстом доступа.

## Почему auth-check не должен жить в каждом route
Если каждый endpoint сам читает header и сравнивает токен со строкой, быстро появляются проблемы:
- проверка размазывается по коду;
- контракты ошибок расходятся;
- часть route забывает сделать ту же самую проверку;
- поменять правило доступа становится дорого.

Поэтому auth-check лучше выносить в dependency или отдельный auth service.

## Что здесь считается хорошим актором
На этом уровне actor context обычно содержит минимум:
- `actor_id`;
- `role`;
- иногда `token_type` или `api_key_name`.

То есть dependency не просто говорит "доступ есть", а возвращает данные, которые сервис потом может использовать в правилах.

## `401` и `403` — не одно и то же
Базовая модель:
- `401 Unauthorized` — нет валидной аутентификации;
- `403 Forbidden` — аутентификация есть, но права недостаточны.

Практический смысл такой:
- неверный токен -> `401`;
- валидный токен обычного пользователя, который лезет в admin route -> `403`.

## Что dependency должна делать
Dependency может:
- прочитать headers;
- проверить token;
- собрать actor context;
- остановить запрос через `HTTPException`.

Но dependency не должна превращаться в сервис бизнес-правил. Если там уже живёт логика "можно ли закрывать заказ, если он оплачен", это уже не auth-layer.

## Типичные ошибки
- route сам сравнивает token вместо dependency;
- `200 OK` с текстом `invalid token` вместо настоящего `401`;
- auth context не возвращается, и ниже снова читаются headers вручную;
- auth и permission логика смешаны в один нечитаемый if-block.

## Что нужно понять перед практикой
Перед `practice.py` должно быть ясно:
1. зачем превращать header в actor context;
2. почему `401` и `403` должны различаться;
3. почему auth-check лучше централизовать в dependency.
