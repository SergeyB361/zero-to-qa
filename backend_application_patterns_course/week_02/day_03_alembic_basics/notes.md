# Alembic Basics

## Когда тема нужна
Пока сервис живёт как учебный прототип, можно собирать таблицы через `Base.metadata.create_all()`. Но как только схема начинает меняться между версиями сервиса, этого уже недостаточно.

Нужна история изменений схемы.

Именно это и даёт Alembic:
- фиксирует изменение как revision;
- позволяет применять изменения по порядку;
- делает schema evolution воспроизводимой на разных окружениях.

## Главная проблема без миграций
Если ты просто поменял ORM-модель, это ещё не значит, что БД изменилась.

То есть у тебя могут разъехаться:
- Python-модели;
- реальная схема в базе;
- данные, которые уже лежат в таблицах.

Без миграций это заканчивается случайным ручным SQL или полным пересозданием базы.

## Как мыслить правильно
Полезная ментальная модель такая:
1. модель описывает желаемое состояние;
2. migration описывает путь из старого состояния в новое;
3. revision history хранит этот путь как последовательность шагов.

Это означает, что менять схему нужно не мыслью "я добавил поле в class", а мыслью "я спланировал upgrade path для живой базы".

## Что обычно делает revision
На базовом уровне revision отвечает на три вопроса:
- от какой версии схемы мы идём (`down_revision`);
- к какой новой версии идём (`revision`);
- какие шаги выполняются в `upgrade()`.

Иногда ещё есть `downgrade()`, но в реальных командах отношение к downgrade аккуратное: не каждое изменение откатывается безопасно.

## Почему autogenerate не освобождает от мышления
Alembic умеет помочь diff-ом, но автогенерация не означает, что миграцию можно применять не глядя.

Нужно отдельно проверять:
- безопасно ли добавляется non-null колонка;
- не нужен ли backfill;
- не ломается ли существующий код;
- не делает ли миграция опасный rewrite таблицы.

## Что полезно держать в голове
### `create_all()`
Создаёт схему "как будто база пустая".

### `revision`
Фиксирует изменение как версионированный шаг.

### `upgrade head`
Доводит схему до последней версии.

### migration script
Не просто декларация, а реальный operational plan для живой базы.

## Типичные ошибки
- считать, что изменение ORM-модели автоматически меняет БД;
- редактировать уже применённую migration "задним числом";
- добавлять non-null колонку без плана заполнения существующих строк;
- не проверять migration на копии реальных данных;
- путать "мне удобно локально" и "это безопасно для окружения".

## Что нужно понять перед практикой
Перед `practice.py` должно быть ясно:
1. чем migration отличается от изменения ORM-модели;
2. зачем нужны `revision` и `down_revision`;
3. почему migration — это управляемая последовательность SQL-шагов, а не магия.
