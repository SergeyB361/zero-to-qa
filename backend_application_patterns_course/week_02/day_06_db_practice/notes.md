# DB Practice

## Что это за день
Это не новый isolated topic. Это сборка недели в одну связную практику.

Здесь должны одновременно читаться:
- settings с `database_url`;
- engine/session factory;
- repository;
- service;
- transaction boundary;
- доменные ошибки.

Если после этой недели всё ещё хочется писать SQLAlchemy-сессию прямо в route, значит предыдущие дни были прочитаны, но не собраны в систему.

## Как мыслить про runtime
Полезно разделять три уровня.

### Runtime assembly
Кто и как создаёт engine, session factory и зависимости.

### Data access
Кто читает и пишет строки в БД.

### Business flow
Кто решает, что именно считается успешным сценарием и где проходит commit/rollback.

## Что должно получиться на практике
На базовом уровне нормальный flow выглядит так:
1. settings дают `database_url`;
2. runtime создаёт engine и `SessionLocal`;
3. repository умеет читать и писать сущность;
4. service владеет `commit()` / `rollback()`;
5. доменная ошибка поднимается уже в понятном виде.

Это уже похоже на реальный backend-slice, а не на разрозненные сниппеты.

## Что здесь особенно важно
### Session factory
Она должна создаваться один раз для данного runtime, а не по случайным местам в коде.

### Repository
Должен быть тупым и предсказуемым: create/list/get.

### Service
Должен собирать сценарий и владеть транзакционной границей.

## Типичные ошибки
- создавать engine прямо внутри service метода;
- коммитить внутри repository;
- смешивать config, ORM и бизнес-ошибки в одной функции;
- делать runtime, который невозможно протестировать отдельно.

## Что нужно понять перед практикой
Перед `practice.py` должно быть ясно:
1. зачем нужен `build_session_factory(settings)`;
2. почему repository не должен владеть commit/rollback;
3. как собрать из config + ORM + service минимальный backend runtime.
