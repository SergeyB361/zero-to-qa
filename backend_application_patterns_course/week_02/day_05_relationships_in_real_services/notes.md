# Relationships in Real Services

## Когда тема нужна
Как только в сервисе появляется не одна таблица, а связь между сущностями, уже недостаточно думать только отдельными CRUD-операциями.

Например:
- у `Project` есть много `Task`;
- у `User` есть много `Order`;
- у `Account` есть много `Membership`.

Здесь начинаются реальные backend-вопросы:
- как моделировать связь в ORM;
- как загружать связанные данные без хаоса;
- где проходит граница между удобством и скрытой дорогой query.

## Что relationship даёт на практике
Relationship нужен не ради красивого API `project.tasks`.

Он нужен, чтобы:
- выразить связь на уровне модели;
- писать понятные запросы со связанными сущностями;
- управлять loading strategy;
- держать доменную модель ближе к реальным данным.

## Почему нельзя просто везде писать `obj.related`
Если не думать о loading strategy, relationship легко превращается в источник скрытых запросов.

То есть код выглядит безобидно:
```python
project.tasks
```
но под капотом это может вызвать дополнительный SQL.

Отсюда возникают типичные проблемы:
- `N+1`;
- случайные lazy-load в сериализации;
- непредсказуемое число запросов на endpoint.

## Полезная ментальная модель
Полезно мыслить так:
1. relationship описывает структуру домена;
2. query strategy описывает, как именно ты хочешь загрузить данные сейчас;
3. service решает, какой набор данных нужен сценарию.

То есть relationship и loading strategy — это не одно и то же.

## Что чаще всего нужно на junior-уровне
На этом уровне достаточно уверенно понимать:
- `one-to-many`;
- `back_populates`;
- `ForeignKey`;
- `selectinload` как практичный способ заранее загрузить связанные коллекции.

`selectinload` здесь полезен, потому что он:
- не прячет связь;
- явно показывает намерение;
- часто хорошо подходит для list/read сценариев.

## Где проходит граница ответственности
- model описывает связь;
- repository/service выбирает стратегию загрузки;
- router не должен случайно триггерить lazy-load во время сборки ответа.

Если response строится прямо из ORM-объекта без контроля запросов, ты быстро теряешь предсказуемость.

## Типичные ошибки
- сериализовать ORM-объект и надеяться, что всё само подтянется правильно;
- грузить связанную коллекцию по одному объекту в цикле;
- не думать, нужен ли тебе `selectinload` в конкретном сценарии;
- держать relationship, но продолжать вручную писать разрозненные запросы без системы.

## Что нужно понять перед практикой
Перед `practice.py` должно быть ясно:
1. зачем relationship полезен сверх простого `ForeignKey`;
2. почему loading strategy нужно выбирать явно;
3. почему service/repository должен возвращать уже предсказуемо загруженные данные.
