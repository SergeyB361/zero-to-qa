# Schema Evolution Cases

## Когда эта тема нужна
Не каждое изменение схемы одинаково безопасно.

Добавить nullable колонку — обычно простой сценарий.
Добавить non-null колонку в таблицу с уже существующими строками — уже другой класс риска.
Удалить колонку или поменять смысл данных — ещё более опасный сценарий.

Поэтому после базового понимания Alembic нужен следующий уровень: уметь оценивать риск изменения схемы до того, как ты нажал `upgrade`.

## Как мыслить правильно
Полезный вопрос не "какой SQL написать", а "как эта миграция поведёт себя на живой базе с уже существующими данными".

Значит, нужно заранее различать типы кейсов.

## Частый простой кейс
### Добавить nullable колонку
Обычно безопасно, потому что старые строки могут временно жить с `NULL`.

Например:
- добавили `avatar_url`;
- существующие users пока без значения;
- приложение переживает это состояние.

Это хороший пример изменения, которое часто можно катить одной миграцией.

## Более опасный кейс
### Добавить non-null колонку без default
Если в таблице уже есть данные, то БД не знает, чем заполнить существующие строки.

Нормальный plan обычно такой:
1. добавить колонку как nullable или с безопасным default;
2. сделать backfill;
3. только потом ужесточить constraint.

То есть non-null изменение часто требует нескольких шагов, а не одного красивого DDL.

## Очень опасный кейс
### Drop или rename
Удаление или переименование ломает старый код, отчёты, скрипты и интеграции.

Поэтому для таких кейсов полезно думать в терминах compatibility window:
- сначала новый код умеет жить с обоими вариантами;
- потом происходит перенос данных или чтения;
- только после этого старое поле реально убирается.

## Почему schema evolution — это не только DB-задача
Изменение схемы влияет на:
- ORM-модели;
- сервисный код;
- API контракты;
- аналитические запросы;
- тестовые фикстуры.

Если смотреть только на SQL, легко пропустить поломку на уровне приложения.

## Типичные ошибки
- добавлять non-null колонку одним шагом без плана заполнения;
- считать rename "мелочью";
- удалять колонку, которую ещё читает код;
- не думать про backfill и порядок rollout;
- оценивать миграцию только по локальной пустой базе.

## Что нужно понять перед практикой
Перед `practice.py` должно быть ясно:
1. какие изменения обычно low-risk, medium-risk и high-risk;
2. почему non-null изменение часто делается в несколько шагов;
3. почему schema evolution нужно планировать как rollout, а не как одиночный SQL-команду.
