# SQLAlchemy Session Patterns

## Что такое session в практическом смысле
Session — это не просто «объект для запросов». В нормальном backend session — это граница работы с данными в рамках сценария.

Через неё ты:
- читаешь объекты;
- меняешь их состояние;
- добавляешь новые записи;
- коммитишь или откатываешь изменения.

То есть session — это рабочий контекст unit of work.

## Главная проблема
Если непонятно, кто именно владеет `commit()` и `rollback()`, то код быстро становится хрупким:
- repository коммитит сам;
- service тоже коммитит сам;
- route иногда коммитит ещё раз;
- при ошибке часть изменений уже уехала в БД.

## Нормальная граница
На этом уровне полезно держать правило:
- repository работает с данными;
- service решает, когда действие считается завершённым;
- commit/rollback живут в service boundary.

Это не единственный возможный стиль, но он очень практичен для backend-курса и большинства junior-проектов.

## Что важно понять про lifecycle
### `add()`
Объект попадает в session, но ещё не обязательно записан в БД.

### `commit()`
Фиксирует изменения.

### `refresh()`
Подтягивает актуальные значения после commit, например `id`, который выставила БД.

### `rollback()`
Откатывает текущую незакоммиченную транзакцию после ошибки.

## Почему rollback обязателен
Если внутри session произошёл `IntegrityError` и ты не сделал rollback, session остаётся в повреждённом состоянии.

Это означает, что следующий запрос через неё может упасть не потому, что логика плохая, а потому что session не была очищена после ошибки.

## Хорошая инженерная привычка
Когда действие может нарушить constraint, думай так:
1. выполняем операцию;
2. при ошибке делаем rollback;
3. поднимаем понятную доменную ошибку выше.

## Что не стоит делать
- коммитить в repository по каждому методу;
- делать `rollback()` где попало без понимания причины;
- передавать одну и ту же session в случайные фоновые процессы;
- держать session «вечной» глобальной переменной.

## Что нужно понять перед практикой
Перед `practice.py` должно быть ясно:
1. кто владеет commit/rollback;
2. зачем нужен refresh после create;
3. почему после `IntegrityError` session нельзя просто использовать дальше без rollback.
