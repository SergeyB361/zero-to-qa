# Capstone — Backend Service

## Цель capstone
Финальный проект этой программы должен показать не отдельный framework-урок, а собранный backend-service.

То есть здесь проверяется способность соединить в один артефакт:
- FastAPI;
- SQLAlchemy;
- DB-aware runtime;
- auth/roles;
- CRUD patterns;
- tests;
- Docker Compose.

## Что считается сильным результатом
Сильный результат — это не обязательно большой проект. Сильный результат — это цельная система с понятными границами.

На этом уровне достаточно, чтобы в проекте были видны:
- app structure;
- settings/config;
- data model;
- service layer;
- auth/role contract;
- нормальные error responses;
- воспроизводимый запуск.

## Что здесь важнее всего
В capstone важны не лишние фичи, а согласованность.

Например:
- если есть create/update/delete, они должны быть стилистически одинаковыми;
- если есть auth, она должна быть централизована;
- если есть DB, она должна быть встроена в runtime, а не болтаться случайным helper-ом;
- если есть tests, они должны проверять реально важные сценарии.

## Как ограничить scope
Нормальная capstone-стратегия:
1. выбрать одну сущность и понятный workflow вокруг неё;
2. реализовать основной CRUD;
3. добавить auth/roles;
4. добавить tests и compose runtime;
5. только потом думать об extra backlog.

Это лучше, чем сразу пытаться сделать полный production clone реального сервиса.

## Что стоит проверить перед сдачей
Перед тем как считать capstone готовым, полезно убедиться:
1. сервис запускается по понятной инструкции;
2. tests проходят;
3. API-контракты согласованы;
4. create/update/delete/read сценарии реально работают;
5. README объясняет, как проект запускать и что он показывает.

## Что не требуется
Capstone этого курса не обязан включать:
- async SQLAlchemy;
- distributed tracing;
- k8s deployment;
- broker/outbox/event sourcing.

Но если базовые backend patterns не доведены, такие фичи только скрывают проблему, а не решают её.
