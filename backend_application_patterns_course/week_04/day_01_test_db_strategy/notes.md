# Test DB Strategy

## Когда тема нужна
Как только у backend появляются integration tests с реальной БД, нужно решить, как именно эта БД живёт во время тестов.

Если стратегия не выбрана, тесты быстро становятся:
- зависимыми друг от друга;
- медленными и хрупкими;
- непредсказуемыми по данным.

## Главный вопрос недели
Нужно ответить не на вопрос "есть ли у нас тестовая БД", а на вопрос "как мы гарантируем изоляцию сценариев".

Именно изоляция, а не просто наличие отдельного `test.db`, отличает нормальную test strategy от случайного локального прогона.

## Типовые подходы
### In-memory SQLite
Хорошо подходит для быстрых integration-like тестов и учебных примеров.

Плюсы:
- очень быстро;
- легко поднимать на каждый тестовый модуль;
- минимум инфраструктуры.

Минусы:
- это не production Postgres;
- часть поведения может отличаться.

### Отдельная тестовая база
Это уже ближе к реальному backend runtime.

Плюсы:
- выше fidelity;
- можно тестировать реальные SQL/constraints/transaction behavior.

Минусы:
- сложнее setup;
- нужна явная стратегия очистки данных.

## Что именно нужно контролировать
В тестовой стратегии обычно есть три слоя:
1. как создаётся session/engine для тестов;
2. как подготавливаются стартовые данные;
3. как база очищается между сценариями.

Если хотя бы один слой не определён, тесты начинают протекать друг в друга.

## Почему reset важнее, чем кажется
Очень частая ошибка: тесты зелёные по отдельности, но падают пачкой. Почти всегда это значит, что один сценарий оставил после себя данные и второй тест получил неожиданное состояние.

Поэтому полезно мыслить так:
- каждый тест должен либо сам строить мир с нуля;
- либо гарантированно работать в откатываемой транзакции.

## Что подходит для этого курса
На этом уровне достаточно уверенно уметь:
- собрать отдельный `SessionLocal` для тестов;
- заполнить тестовую БД стартовыми данными;
- очистить таблицы перед следующим сценарием;
- понимать, когда этого уже недостаточно и нужен отдельный test Postgres.

## Типичные ошибки
- использовать ту же БД, что и локальное приложение;
- не очищать таблицы между тестами;
- хранить глобальное состояние между тестовыми прогонами;
- называть стратегию "integration tests", когда на самом деле проверяется один helper без DB isolation.

## Что нужно понять перед практикой
Перед `practice.py` должно быть ясно:
1. зачем test DB должна быть изолированной;
2. чем seed и reset различаются по роли;
3. почему тестовая стратегия — это часть архитектуры, а не мелкая техника запуска.
