# Docker Compose: App + DB

## Когда тема нужна
Как только backend перестаёт запускаться одним `uvicorn main:app`, появляется вопрос воспроизводимого runtime:
- как поднять приложение и БД вместе;
- как передать env;
- как понять, что контейнеры реально готовы;
- как дать проекту нормальную точку входа для другого разработчика.

Именно здесь нужен `docker compose`.

## Как мыслить правильно
Compose — это не просто файл с двумя контейнерами. Это описание локального runtime-контракта проекта.

Он должен отвечать на вопросы:
1. какие сервисы нужны приложению;
2. какие переменные окружения они получают;
3. как они видят друг друга по сети;
4. как определяется их готовность.

## Что обычно входит в backend compose runtime
Минимальный набор:
- `app`;
- `db`;
- volume для данных БД;
- env vars вроде `DATABASE_URL`;
- healthchecks;
- проброс нужных портов.

Если этого нет, проект остаётся "рабочим только на машине автора".

## Почему healthcheck важнее `depends_on`
Просто порядок запуска контейнеров ещё не означает готовность приложения.

Postgres может быть запущен как процесс, но ещё не принимать соединения. Поэтому полезно мыслить так:
- `depends_on` задаёт порядок;
- healthcheck задаёт реальную готовность.

## Что полезно централизовать
В compose runtime нужно явно видеть:
- имя сервиса БД;
- `DATABASE_URL`, которая использует внутреннее имя контейнера;
- тома и путь к данным;
- команду запуска app.

Это делает runtime объяснимым, а не магическим.

## Как устроен этот урок
В этом дне практика идёт не через Python-словарь, а через реальный YAML-артефакт:
- `docker-compose.example.yml` — эталон;
- `docker-compose.practice.yml` — файл, который нужно довести до рабочего состояния.

Это важнее для backend-курса, потому что именно такой артефакт студент потом будет редактировать в настоящем проекте.

## Типичные ошибки
- использовать `localhost` внутри контейнера для доступа к БД;
- не задавать healthcheck;
- смешивать dev/test/prod значения env в одном compose без понятной цели;
- хранить состояние БД в контейнере без volume.

## Что нужно понять перед практикой
Перед `practice.py` должно быть ясно:
1. зачем backend compose обычно содержит app и db вместе;
2. почему `DATABASE_URL` внутри compose использует service name, а не `localhost`;
3. почему healthchecks и volumes — это часть нормального runtime, а не факультативная деталь.
