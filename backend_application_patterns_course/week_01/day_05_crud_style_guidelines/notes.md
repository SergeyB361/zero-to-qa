# CRUD Style Guidelines

## Почему CRUD быстро становится хаотичным
На простом backend почти всегда есть базовые операции:
- create;
- list;
- get by id;
- partial update;
- delete.

Именно из-за их «обычности» их часто делают небрежно.

В результате один endpoint:
- возвращает `200` на create;
- другой отдаёт `204` вместе с телом;
- третий на missing item отвечает то `404`, то `200` с `null`.

Это делает API непредсказуемым.

## Что здесь считается хорошим стилем
### Create
Обычно:
- `POST /resources`
- `201 Created`
- ответ содержит созданную сущность или минимально полезный payload.

### List
Обычно:
- `GET /resources`
- `200 OK`
- список сущностей.

### Get by id
Обычно:
- `GET /resources/{id}`
- `200 OK` или `404 Not Found`.

### Partial update
Обычно:
- `PATCH /resources/{id}`
- `200 OK`
- возвращает обновлённую сущность.

### Delete
Есть два нормальных варианта:
- `204 No Content` без тела;
- `200 OK` с полезным ответом, если для клиента это важно.

Главное — выбрать стиль и не прыгать между вариантами хаотично.

## Что ещё важно
CRUD — это не только endpoint-ы, но и смысл операций.

Полезные вопросы:
1. что именно обновляет `PATCH`?
2. удаляем физически или делаем soft delete?
3. что клиент увидит после delete?
4. как ведёт себя API при повторной операции?

## Что делает API удобным
- одинаковая семантика status code;
- одинаковая форма ошибок;
- одинаковая логика response body;
- понятные route names.

## Типичные ошибки
- `POST` возвращает `200`, а `PATCH` — `201` без причины;
- `DELETE` отдаёт тело вместе с `204`;
- отсутствующий ресурс не даёт `404`;
- create/update routes возвращают payload в разном стиле без пользы.

## Что нужно понять перед практикой
Перед `practice.py` должно быть ясно:
1. почему CRUD должен быть консистентным;
2. какие status codes обычно ожидаются от create/get/patch/delete;
3. почему soft delete и hard delete — это разные решения.
