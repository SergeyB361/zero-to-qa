# Settings, Env and Config

## Зачем это вообще нужно
Backend почти никогда не живёт с одним фиксированным набором параметров.

Даже у простого сервиса быстро появляются:
- URL базы;
- debug flag;
- host/port;
- API prefix;
- внешние URL соседних сервисов;
- feature flags.

Если эти значения раскиданы по коду через случайные `os.getenv(...)`, проект становится трудно поддерживать.

## Главная идея
Конфигурация должна иметь:
- одно место входа;
- понятные defaults;
- явное преобразование типов;
- предсказуемые имена переменных окружения.

То есть не так:
```python
if os.getenv('DEBUG') == 'true':
    ...
```

в пяти разных файлах, а так:
- есть объект настроек;
- он собирается один раз;
- остальной код работает уже с готовыми typed values.

## Что обычно попадает в settings
На этом уровне полезно держать в конфиге:
- `APP_NAME`
- `DEBUG`
- `API_PREFIX`
- `DATABASE_URL`
- `PAGE_SIZE`
- URL соседних сервисов

## Почему важны typed values
Переменные окружения приходят строками.

Значит значения вроде:
- `"true"`
- `"0"`
- `"20"`

нужно преобразовать осознанно.

Без этого легко получить баги:
- `bool('false') == True`
- пустая строка случайно считается валидной конфигурацией
- строковый `page_size` сравнивается как число

## Разумная граница
Конфиг не должен знать бизнес-логику.
Его задача: прочитать env, нормализовать значения и собрать удобный объект настроек.

## Типичные ошибки
- читать env прямо внутри route или service;
- размазывать defaults по нескольким файлам;
- не валидировать числа и булевы значения;
- хранить секреты как магические константы в коде.

## Что нужно понять перед практикой
Перед `practice.py` должно быть ясно:
1. зачем собирать config в одном месте;
2. почему типизация env-значений важна;
3. почему route/service не должны сами лазить в `os.getenv`.
