# Project Layout and Layers

## Когда эта тема нужна
Как только backend перестаёт быть файлом на 50 строк, в коде начинает смешиваться всё сразу:
- HTTP;
- бизнес-правила;
- доступ к данным;
- формат ответа;
- конфигурация.

Пока логика маленькая, это терпимо. Но как только появляются новые endpoint-ы, проверки, ошибки и тесты, монолитный файл быстро становится неуправляемым.

## Проблема «толстого route»
Если route-функция одновременно:
- читает входные данные;
- валидирует бизнес-ограничения;
- меняет storage;
- решает, какие ошибки возможны;
- собирает HTTP-ответ,

то у тебя нет границ ответственности.

Это делает код:
- трудно тестируемым;
- неудобным для рефакторинга;
- опасным при расширении.

## Базовые слои, которые здесь нужны
На этом уровне достаточно трёх основных слоёв.

### Router layer
Отвечает за HTTP:
- какой endpoint вызван;
- какие данные пришли;
- какой status code вернуть;
- какой response model использовать.

Router не должен решать бизнес-задачу целиком.

### Service layer
Отвечает за поведение системы:
- что считается корректным действием;
- какие правила применяются;
- в каком порядке выполняются шаги.

Service не должен знать про HTTP-детали вроде `status_code=201`.

### Repository layer
Отвечает за доступ к данным:
- list;
- get by id;
- create;
- update;
- delete.

Repository не должен решать бизнес-логику уровня «можно ли менять статус».

## Как мыслить правильно
Полезный вопрос для каждого куска кода:
1. это HTTP-слой?
2. это бизнес-правило?
3. это доступ к данным?

Если ответов сразу несколько, граница, скорее всего, сломана.

## Нормальная стартовая структура
На junior-уровне не нужен enterprise-каркас на 30 директорий.

Но уже полезно привыкать к понятной структуре:

```text
app/
  main.py
  routers/
  services/
  repositories/
  schemas/
  models/
  config.py
```

Даже если в учебном примере всё находится в одном файле, логически эти слои должны читаться отдельно.

## Что не нужно делать
- Не дроби проект на абстракции без пользы.
- Не делай repository формально, если route всё равно работает с `_items` напрямую.
- Не тащи SQLAlchemy session в router без service layer, если хочешь строить нормальный backend.
- Не путай «много файлов» и «хорошая архитектура».

## Типичные ошибки
- route напрямую создаёт объект и пишет его в список/БД;
- service возвращает `JSONResponse` вместо доменных данных;
- repository знает про `HTTPException`;
- один и тот же бизнес-паттерн копируется по нескольким endpoint-ам.

## Что нужно понять перед практикой
Перед `practice.py` должно быть ясно:
1. зачем route держать тонким;
2. зачем нужен service layer даже на простом CRUD;
3. почему repository должен быть единой точкой работы с данными.
