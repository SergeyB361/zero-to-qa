# Error Handling and API Contracts

## Почему это отдельная тема
Backend быстро становится неудобным, если ошибки отдаются хаотично.

Один endpoint отвечает:
```json
{"error": "not found"}
```

второй:
```json
{"detail": "missing item"}
```

третий просто кидает дефолтный traceback или случайный `500`.

Это плохо не только для клиента API, но и для тестов.

## Что значит API contract для ошибок
Контракт — это договорённость о форме ответа:
- какой status code вернуть;
- какое поле содержит описание ошибки;
- есть ли машинно-читаемый `code`;
- какие сценарии считаются `404`, `409`, `422` и т.д.

То есть ошибка тоже часть API, а не побочный шум.

## Что здесь важно различать
### `404 Not Found`
Когда ресурса нет.

### `409 Conflict`
Когда действие конфликтует с текущим состоянием системы.
Пример: пытаемся создать проект с уже занятым `slug`.

### `422 Unprocessable Entity`
Когда запрос синтаксически корректен, но не проходит валидацию на уровне схемы.
FastAPI часто делает это автоматически через Pydantic.

## Хороший стиль
Полезно, когда backend возвращает что-то вроде:
```json
{
  "detail": "project slug already exists",
  "code": "project_conflict"
}
```

Это лучше, чем случайная строка без структуры.

## Где должна жить ошибка
Есть два разумных шага:
1. service или domain layer поднимает понятную предметную ошибку;
2. HTTP-слой переводит её в согласованный API response.

То есть service не обязан сам знать про JSON-ответ, но он должен явно сигнализировать, что произошло.

## Типичные ошибки
- кидать `HTTPException` глубоко в repository;
- использовать `500` там, где нужен `404` или `409`;
- не фиксировать формат ошибки;
- смешивать текст для человека и код для машины в одну неструктурированную строку.

## Что нужно понять перед практикой
Перед `practice.py` должно быть ясно:
1. ошибка — часть контракта API;
2. `404` и `409` означают разные вещи;
3. сервисная ошибка и HTTP-ответ — не одно и то же, но должны быть согласованы.
