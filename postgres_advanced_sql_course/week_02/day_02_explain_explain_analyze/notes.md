# EXPLAIN и EXPLAIN ANALYZE

## Когда это нужно
Разговор о производительности бессмысленен, если ты не видишь, как Postgres реально собирается выполнять запрос.

`EXPLAIN` и `EXPLAIN ANALYZE` нужны, чтобы перестать гадать и увидеть:
- будет ли последовательное чтение;
- используется ли индекс;
- в каком порядке идут join'ы;
- сколько реально строк обработано;
- насколько твоя оптимизация изменила execution plan.

## Как об этом думать
SQL описывает, что нужно получить.
План запроса показывает, как Postgres собирается это сделать.

Это отдельный слой понимания: не логика результата, а стоимость получения результата.

## Разница между EXPLAIN и EXPLAIN ANALYZE
- `EXPLAIN` показывает предполагаемый план;
- `EXPLAIN ANALYZE` реально выполняет запрос и показывает фактические числа.

Поэтому `EXPLAIN ANALYZE` полезнее, но он действительно запускает запрос.

## Базовый синтаксис
```sql
EXPLAIN
SELECT *
FROM tasks
WHERE status = 'open';

EXPLAIN ANALYZE
SELECT *
FROM tasks
WHERE status = 'open';
```

## Что смотреть в плане
На базовом уровне достаточно уверенно замечать:
- `Seq Scan` — полное чтение;
- `Index Scan` / `Bitmap Index Scan` — чтение через индекс;
- estimated rows vs actual rows;
- timing и loops в `EXPLAIN ANALYZE`.

## Почему это важнее интуиции
Запрос может выглядеть коротким, но работать плохо.
Запрос может выглядеть длинным, но выполняться адекватно.

Без плана performance-обсуждение быстро превращается в догадки.

## Типичные ошибки
- обсуждать производительность без `EXPLAIN`;
- путать `EXPLAIN` и `EXPLAIN ANALYZE`;
- запускать `EXPLAIN ANALYZE` на изменяющем запросе без понимания последствий;
- смотреть только на наличие индекса, но не на выбранный план.

## Что нужно понимать перед практикой
Перед `practice.sql` ты должен понимать:
1. зачем нужен `EXPLAIN`;
2. чем отличается `EXPLAIN ANALYZE`;
3. как заметить базовые признаки плохого и хорошего плана.
