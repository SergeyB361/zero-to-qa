# UI: продвинутый уровень, День 6 — Debugging UI failures

## Когда это нужно

UI-тесты падают шумно: локатор не найден, элемент перекрыт, действие не произошло, assertion не совпал. Без системного подхода расследование превращается в угадайку.

Debugging UI failures нужен, чтобы падение превращалось в воспроизводимый технический кейс.

## Как об этом думать

Хороший mental model: UI failure нужно локализовать по слою проблемы.

Обычно причины лежат в одном из слоёв:
- неправильный локатор;
- неверное ожидание состояния;
- сеть или backend;
- тестовые данные;
- реальный UI defect;
- проблема окружения или браузера.

То есть вопрос не “почему тест красный”, а “на каком слое сломался сценарий”.

## Какие артефакты особенно полезны

- screenshot;
- video;
- trace;
- request/response контекст;
- лог последнего шага;
- DOM/state snapshot при падении.

Хорошее расследование начинается с нормальных материалов, а не с повторного запуска вслепую.

## Частые ошибки

- смотреть только на stack trace;
- сразу обвинять flaky infrastructure без признаков;
- не различать data/setup defect и UI defect;
- не сохранять trace или screenshot, когда они реально нужны.

## Что важно перед практикой

Перед `practice.py` ты должен понимать:
1. UI failure нужно раскладывать по слоям причин;
2. debugging начинается с артефактов, а не с гадания;
3. сильный UI-suite должен помогать расследованию, а не только сообщать о падении.

## Что делать дальше

1. Открой `examples.py` и посмотри, как один failure разбирается пошагово.
2. Затем переходи к `practice.py`.
3. В каждом задании сначала отвечай, какой следующий артефакт даст тебе больше всего сигнала о причине падения.
