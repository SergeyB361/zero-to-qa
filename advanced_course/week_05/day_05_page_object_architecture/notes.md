# UI: продвинутый уровень, День 5 — Page Object architecture

## Когда это нужно

Когда UI-suite растёт, тесты начинают дублировать действия, локаторы и технические шаги. Без архитектуры они быстро превращаются в набор copy-paste сценариев.

POM и page object architecture нужны, чтобы отделить сценарий теста от механики страницы.

## Как об этом думать

Хороший mental model:
- test описывает бизнес-сценарий;
- page object скрывает детали взаимодействия со страницей;
- page component выделяет повторяющийся кусок интерфейса;
- reusable flow собирает типовые последовательности шагов.

Важно: page object не должен прятать смысл теста. Он должен прятать механику.

## Что хорошая архитектура даёт practically

- меньше дублирования локаторов и действий;
- проще поддерживать UI-suite при изменении интерфейса;
- тесты читаются как сценарии, а не как низкоуровневые команды;
- компоненты и flows можно переиспользовать осознанно.

## Что делает архитектуру плохой

Плохие признаки:
- один God object на весь UI;
- бизнес-assertions живут внутри page object;
- `BasePage` разрастается десятками случайных методов;
- page object знает слишком много о тестовом контексте.

## Частые ошибки

- прятать в page object то, что должно быть видно в тесте;
- делать reuse любой ценой;
- строить абстракции раньше, чем появились повторяющиеся паттерны;
- смешивать page object, test data и assertions в одном классе.

## Что важно перед практикой

Перед `practice.py` ты должен понимать:
1. page object скрывает механику, но не бизнес-смысл теста;
2. компоненты и flows нужны для управляемого переиспользования;
3. архитектура должна уменьшать стоимость изменений, а не делать UI-suite умнее на словах.

## Что делать дальше

1. Открой `examples.py` и посмотри, как test, page object и component разделяются по ответственности.
2. Затем переходи к `practice.py`.
3. В каждом задании сначала определяй, что должно жить в тесте, а что в page layer.
