# UI: качество и масштабирование, День 4 — Test data in UI tests

## Когда это нужно

UI-тесты особенно чувствительны к данным: от них зависит видимость элементов, порядок сценария, доступность действий и итоговые assertions.

Без нормальной стратегии данных UI-suite быстро становится flaky и трудно воспроизводимым.

## Как об этом думать

Хороший mental model: данные для UI-тестов — это часть сценария, а не фон.

Нужно осознанно выбирать:
- что создавать на лету;
- что брать из seeded environment;
- какие данные нужны для разных ролей и состояний;
- как сделать начальное состояние воспроизводимым.

## Почему это особенно сложно в UI

В UI данные часто влияют сразу на несколько слоёв:
- backend state;
- видимость и порядок элементов;
- разрешённые действия;
- визуальные и текстовые assertions.

То есть плохие данные ломают не только сценарий, но и дебаг причин падения.

## Частые ошибки

- использовать shared state между UI-тестами;
- зависеть от данных, происхождение которых никто не контролирует;
- создавать слишком тяжёлый setup ради простого сценария;
- не различать данные для smoke и для тяжёлых end-to-end flows.

## Что важно перед практикой

Перед `practice.py` ты должен понимать:
1. UI data strategy должна быть такой же явной, как и API data strategy;
2. данные должны делать сценарий воспроизводимым;
3. чем меньше неявного состояния, тем дешевле сопровождение UI-suite.

## Что делать дальше

1. Открой `examples.py` и посмотри, как данные влияют на стабильность UI-flow.
2. Затем переходи к `practice.py`.
3. В каждом задании сначала определяй, какое минимальное состояние данных нужно для прохождения сценария.
