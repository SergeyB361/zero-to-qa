# UI: качество и масштабирование, День 5 — Parallel UI execution

## Когда это нужно

UI-suite без параллелизма быстро становится слишком медленным. Но просто включить parallel run недостаточно: часть сценариев после этого начинает конфликтовать по данным, сессиям и окружению.

Parallel execution нужен как управляемая стратегия ускорения, а не как переключатель “быстрее”.

## Как об этом думать

Хороший mental model: safe parallelism возможен только там, где тесты достаточно изолированы.

Нужно понимать:
- какие тесты используют общие данные;
- где конфликтуют аккаунты и сессии;
- какие сценарии меняют одно и то же состояние;
- где инфраструктура сама становится bottleneck.

## Что делает parallel run хорошим

- тесты изолированы по данным и окружению;
- сессии и аккаунты не конфликтуют;
- flaky rate не растёт пропорционально скорости;
- suite ускоряется без потери доверия к результату.

## Где ошибаются чаще всего

- включают parallelism без data isolation;
- гоняют stateful сценарии параллельно, хотя они конфликтуют;
- не различают safe parallel group и serial-only scenarios;
- измеряют только скорость, а не качество сигнала.

## Что важно перед практикой

Перед `practice.py` ты должен понимать:
1. parallel execution требует изоляции, а не просто флага запуска;
2. часть UI-сценариев безопасна для параллели, часть нет;
3. ускорение полезно только если доверие к suite не падает.

## Что делать дальше

1. Открой `examples.py` и посмотри, как тесты делятся на safe-parallel и serial groups.
2. Затем переходи к `practice.py`.
3. В каждом задании сначала отвечай, что именно может конфликтовать при параллельном запуске.
