# UI: качество и масштабирование, День 6 — CI for UI tests

## Когда это нужно

UI-тесты в локальной среде — это только половина картины. Как только они начинают жить в CI, появляются новые требования: стабильное окружение, артефакты, browser scope, таймауты и воспроизводимость.

## Как об этом думать

Хороший mental model: CI для UI — это не просто “запусти браузер в пайплайне”, а способ получать повторяемый сигнал о качестве интерфейса после каждого изменения.

Для этого нужны:
- понятный browser scope;
- разделение smoke и full runs;
- пригодные для расследования артефакты;
- контролируемая среда запуска.

## Что это даёт practically

- автоматический сигнал о регрессии UI;
- меньше зависимости от локальной машины инженера;
- более дисциплинированная стабилизация suite;
- понятный набор материалов после падения.

## Где ошибаются чаще всего

- тащат в PR pipeline слишком тяжёлый UI regression;
- не сохраняют trace/screenshot/video;
- не различают browser scope и test scope;
- запускают UI в CI без стабилизации данных и окружения.

## Что важно перед практикой

Перед `practice.py` ты должен понимать:
1. CI для UI требует отдельного дизайна, а не просто переноса локального запуска;
2. smoke и full suite обычно живут по-разному;
3. артефакты и reproducibility — критичная часть UI CI.

## Что делать дальше

1. Открой `examples.py` и посмотри, как UI-run адаптируется под CI.
2. Затем переходи к `practice.py`.
3. В каждом задании сначала формулируй, какой UI-signal нужен в CI быстро, а какой можно оставить для более тяжёлого прогона.
