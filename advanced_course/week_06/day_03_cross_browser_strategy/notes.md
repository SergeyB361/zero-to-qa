# UI: качество и масштабирование, День 3 — Cross-browser strategy

## Когда это нужно

Поддержка нескольких браузеров быстро превращается в дорогое упражнение, если запускать всё везде без стратегии.

Cross-browser testing нужен не для галочки, а для управляемого распределения риска между браузерами и типами сценариев.

## Как об этом думать

Хороший mental model: cross-browser strategy — это решение о том,
- что запускать во всех браузерах;
- что запускать только в основном браузере;
- какие браузеры дают максимальный риск-покрывающий сигнал.

То есть стратегия должна учитывать:
- долю браузеров у продукта;
- критичность user flows;
- стоимость прогона и сопровождения;
- историю browser-specific regressions.

## Что обычно делают practically

- один основной браузер для полного прогона;
- browser matrix для smoke/critical flows;
- отдельные targeted checks для рискованных зон;
- периодический расширенный прогон по нескольким браузерам.

## Частые ошибки

- прогонять весь suite во всех браузерах без приоритета;
- не различать smoke и regression scope;
- не учитывать, какие баги реально бывают browser-specific;
- объявлять cross-browser support, не имея стратегии сопровождения.

## Что важно перед практикой

Перед `practice.py` ты должен понимать:
1. cross-browser coverage должна быть risk-based;
2. один браузер для всего не всегда достаточно, но все браузеры для всего — тоже плохая стратегия;
3. browser matrix — это инженерное решение, а не список пожеланий.

## Что делать дальше

1. Открой `examples.py` и посмотри, как browser scope связывается с риском и стоимостью.
2. Затем переходи к `practice.py`.
3. В каждом задании сначала формулируй, какой браузерный риск ты хочешь покрыть и насколько часто его нужно проверять.
