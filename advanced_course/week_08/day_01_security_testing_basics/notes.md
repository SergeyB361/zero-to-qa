# Senior QA Engineering, День 1 — Security testing basics

## Когда это нужно

Даже если в команде есть отдельные security-специалисты, большая часть уязвимостей сначала проявляется как обычные продуктовые или интеграционные дефекты.

Поэтому QA на senior-уровне должен уметь замечать базовые security-риски в повседневных сценариях:
- аутентификация;
- авторизация;
- обработка входных данных;
- утечка чувствительной информации.

## Как об этом думать

Security testing на этом уровне — не про экзотические эксплойты. Это про привычку смотреть на систему не только как на “что должно работать”, но и как на “что нельзя позволить сделать”.

Хороший mental model:
1. кто пользователь или актор;
2. какие у него должны быть права;
3. какие данные он должен и не должен видеть;
4. что будет, если подать неожиданный ввод или обойти обычный UI-flow.

То есть security mindset начинается с abuse thinking, а не с pentest-экзотики.

## Что проверять в первую очередь

Базовый набор security checks обычно включает:
- проверку доступа к ресурсам без логина;
- проверку доступа с чужой ролью;
- защиту от чтения или изменения чужих данных;
- валидацию входных данных;
- отсутствие секретов, токенов и чувствительных данных в логах и ответах;
- корректное поведение при истекших токенах и невалидных сессиях.

## Почему это важно для QA

Многие серьёзные дефекты выглядят как обычные product bugs, пока на них не посмотришь через призму доступа и данных.

Например:
- пользователь видит чужой заказ;
- endpoint принимает действие без нужной роли;
- в error response утекает внутренний stack trace или токен.

Это всё security-проблемы, хотя обнаружить их можно обычными тестовыми сценариями.

## Частые ошибки

- считать security задачей только отдельной команды;
- проверять только логин и забывать про права доступа;
- тестировать happy path auth, но не отрицательные сценарии;
- логировать чувствительные данные в тестах и артефактах;
- путать “прошёл функционально” и “безопасен”.

## Что важно перед практикой

Перед `practice.py` ты должен понимать:
1. разницу между authentication и authorization;
2. почему security начинается с role/data boundaries;
3. какие базовые проверки можно и нужно встроить в обычный QA-процесс.

## Что делать дальше

1. Открой `examples.py` и посмотри на базовые security scenarios для API и UI.
2. Затем переходи к `practice.py`.
3. В каждом задании сначала формулируй: что злоумышленник или лишённый прав пользователь не должен суметь сделать.
