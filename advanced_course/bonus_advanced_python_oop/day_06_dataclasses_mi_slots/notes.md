# Bonus Advanced Python OOP, День 6 - Data classes, multiple inheritance и __slots__

## Зачем это нужно

К этому моменту у тебя уже есть несколько advanced OOP-инструментов. Но в реальном
коде важен не сам факт “магических методов”, а то, как собирать модели разумно и без
лишнего шума.

В этом уроке три темы:
- `dataclasses` как способ описывать модели короче;
- multiple inheritance как способ собирать mixin-поведение;
- `__slots__` как способ ограничивать атрибуты и экономить память.

Это три разных инструмента, но у них одна общая идея: делать модели точнее.

## Data classes

`dataclass` полезен, когда класс в основном хранит данные.

Вместо ручного написания:
- `__init__`
- `__repr__`
- `__eq__`

можно получить это автоматически.

Пример:

```python
from dataclasses import dataclass

@dataclass
class EventKey:
    event_type: str
    entity_id: str
```

Это уже даёт:
- удобный `__init__`;
- читаемый `__repr__`;
- equality по полям.

## Когда dataclass особенно уместен

Обычно это:
- value objects;
- DTO;
- события;
- конфигурационные записи;
- небольшие доменные модели без сложной инициализации.

## Полезные параметры dataclass

### frozen=True

Делает объект логически неизменяемым.

Это хороший выбор для:
- идентификаторов;
- ключей событий;
- value objects.

### slots=True

Просит dataclass создать slots-структуру вместо обычного `__dict__`.

Это полезно, когда:
- объектов много;
- модель стабильна;
- не нужен динамический набор атрибутов.

## Multiple inheritance

Множественное наследование в Python возможно, но применять его нужно аккуратно.

Самый здоровый сценарий - mixin-классы.

То есть маленькие классы, которые добавляют одно понятное поведение:
- сериализация;
- timestamps;
- soft delete helpers;
- display helpers.

## Когда multiple inheritance нормально

Хороший пример:

```python
class ToDictMixin:
    ...

class DisplayMixin:
    ...

class TaskRecord(DisplayMixin, ToDictMixin):
    ...
```

Здесь каждый mixin решает отдельную задачу, а итоговый класс просто собирает их вместе.

## Когда multiple inheritance становится плохой идеей

Плохо, когда:
- оба родителя содержат тяжёлую бизнес-логику;
- оба имеют сложные `__init__`;
- становится трудно понять MRO;
- поведение класса больше неочевидно по имени и структуре.

## super() и cooperative inheritance

Если несколько родителей используют `__init__`, важна дисциплина:
- принимать `**kwargs`;
- вызывать `super().__init__(...)`;
- не обрывать цепочку.

Иначе один из родителей может просто не инициализироваться.

## Что такое MRO

MRO - это порядок, в котором Python ищет методы в иерархии классов.

Полезно иногда печатать:

```python
print(MyClass.__mro__)
```

чтобы увидеть, в каком порядке реально идут базовые классы.

## __slots__

По умолчанию экземпляры Python обычно хранят атрибуты в `__dict__`.

`__slots__` позволяет явно зафиксировать набор допустимых полей.

Пример:

```python
class Point:
    __slots__ = ("x", "y")
```

Теперь объект:
- не сможет получить случайный новый атрибут;
- не будет хранить обычный `__dict__`.

## Когда __slots__ полезен

Используй `__slots__`, если:
- объектов очень много;
- модель стабильна;
- не нужен свободный динамический набор атрибутов.

Это не “ускоритель по умолчанию”, а более строгий контракт структуры объекта.

## Ограничения __slots__

С `__slots__` неудобнее:
- динамически навешивать новые поля;
- использовать некоторую introspection-логику;
- писать часть очень гибких моделей.

Поэтому `__slots__` нужен не всегда.

## Практический смысл для QA и backend

### Dataclass

Подходит для:
- `EventKey`
- `TestCaseSummary`
- `ApiResult`
- `Coordinate`

### Mixins

Подходят для:
- `to_dict()`
- `display_name()`
- `touch()`
- `mark_deleted()`

### __slots__

Подходит для:
- небольших стабильных структур;
- большого числа value objects;
- объектов, где хочется запретить случайные поля.

## Частые ошибки

### 1. Использовать dataclass для слишком сложной сущности

Если в модели много правил, побочных эффектов и lifecycle-логики, dataclass не всегда лучший выбор.

### 2. Делать multiple inheritance ради “красоты”

Если можно обойтись обычной композицией или одним базовым классом, часто это лучше.

### 3. Добавлять __slots__ без понимания trade-off

Если объект должен оставаться гибким, `__slots__` только мешает.

## Практическое правило для курса

Хорошая стратегия такая:

1. value objects - сначала смотри в сторону `dataclass`;
2. повторяющееся маленькое поведение - в mixin;
3. `__slots__` - только если структура объекта действительно фиксирована.
