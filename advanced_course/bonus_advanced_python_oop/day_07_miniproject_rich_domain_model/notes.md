# Bonus Advanced Python OOP, День 7 - Мини-проект: Rich domain model

## Цель дня

Сегодня задача не в том, чтобы выучить ещё один отдельный магический метод.

Нужно собрать несколько advanced OOP-техник в одну небольшую, но связную модель:
- value objects;
- descriptors;
- callable validator;
- dynamic attribute access;
- dataclass и slots;
- mixin-поведение.

Если после этого дня всё ещё хочется писать “просто класс с полями”, значит advanced
часть пока не начала работать как инструмент проектирования.

## Что именно ты строишь

Небольшую доменную модель для task/event-сценария:
- есть `TaskId` как value object;
- есть `TaskDraft` с валидацией полей;
- есть `TaskRecord` как более строгая модель данных;
- есть `StatusTransitionValidator`;
- есть `EventPayloadView` для динамического чтения payload;
- есть mixin-поведение для представления/сериализации.

Это не production framework. Это компактный учебный проект, который показывает,
что ты умеешь выбирать OOP-инструменты осмысленно.

## Что важно в этом проекте

### 1. Каждая техника должна быть оправдана

Не нужно тащить advanced OOP “ради галочки”.

Если ты добавил descriptor, должно быть понятно:
- какую общую валидацию он решает;
- почему здесь не хватило `property`.

Если ты добавил `__getattr__`, должно быть понятно:
- какой fallback он даёт;
- почему это лучше явного набора полей.

### 2. Модель должна оставаться читаемой

Это частая проблема advanced OOP:
- возможностей много;
- код быстро становится слишком “умным”.

Правильный результат здесь - не максимальная магия, а хорошая инженерная ясность.

### 3. Нужен demo flow

Мини-проект должен запускаться и показывать:
- создание идентификатора;
- сравнение value objects;
- валидацию статуса;
- чтение payload через атрибуты;
- итоговое представление модели в `main()`.

## Рекомендуемый порядок реализации

1. Сначала реализуй `TaskId`.
2. Потом descriptors для полей `title` и `status`.
3. Затем callable validator.
4. Потом `EventPayloadView`.
5. Затем `TaskRecord` как dataclass.
6. В конце собери `main()` и проверь demo flow.

Этот порядок уменьшает хаос. Если сразу бросаться в итоговый класс, ошибки будет труднее локализовать.

## На что смотреть при самопроверке

- `__repr__` действительно помогает отлаживать модель?
- `TaskId("TASK-1") == TaskId("TASK-1")` работает как value equality?
- invalid status реально режется, а не просто сохраняется?
- `payload_view.actor_id` читается через `__getattr__`?
- `TaskRecord` остаётся понятным, а не “магическим монстром”?
