# Test Data Engineering, День 2 — Builder pattern

## Когда это нужно

Factory хороша для простых объектов. Но когда у сущности много полей, переходов состояния и вариаций, один factory начинает разрастаться.

Builder pattern нужен, когда тестовые данные собираются по шагам.

## Как об этом думать

Хороший mental model: builder — это конструктор тестового объекта с fluent API.

Он полезен, когда ты хочешь писать сценарий сборки так:
- взять валидный объект;
- поменять часть полей;
- явно отметить состояние;
- в конце получить готовый payload или модель.

Builder особенно хорош там, где важна читаемость цепочки изменений.

## Чем builder отличается от factory

Factory отвечает на вопрос: “дай мне объект”.

Builder отвечает на вопрос: “собери мне объект вот с такими пошаговыми изменениями”.

То есть factory чаще про defaults, builder — про выразительную настройку.

## Что builder даёт practically

- уменьшает хаос в объектах с множеством полей;
- помогает читать тест как сценарий;
- облегчает создание сложных комбинаций данных;
- отделяет шаги сборки от деталей структуры.

## Частые ошибки

- использовать builder для простого объекта, где хватило бы factory;
- делать builder mutable и неочевидным для повторного использования;
- добавлять цепочки, которые скрывают смысл теста;
- смешивать в builder и данные, и assertions.

## Что важно перед практикой

Перед `practice.py` ты должен понимать:
1. builder полезен, когда объект строится по шагам;
2. его основная сила — читаемость и управляемая вариативность;
3. builder не должен превращаться в ceremony без выигрыша.
