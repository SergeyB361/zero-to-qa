# Test Data Engineering, День 4 — Property-based testing

## Когда это нужно

Обычные example-based tests проверяют несколько заранее выбранных кейсов. Этого часто достаточно, но иногда важнее проверить не отдельный пример, а инвариант на широком классе входов.

Именно для этого нужен property-based testing.

## Как об этом думать

Property — это правило, которое должно оставаться истинным для множества входных данных.

Хороший mental model:
- example-based test спрашивает: “что произойдёт на этом примере?”
- property-based test спрашивает: “какое правило должно быть верно для всех допустимых входов?”

Это особенно полезно для:
- pure functions;
- преобразований данных;
- нормализации строк и коллекций;
- парсеров, валидаторов и сериализации.

## Что делает свойство хорошим

Сильное свойство:
- формулируется однозначно;
- не привязано к одному примеру;
- проверяет поведение, а не implementation details;
- имеет понятный oracle.

Примеры:
- `abs(x) >= 0`;
- сортировка сохраняет длину коллекции;
- нормализация email делает строку lowercase и trim-ит пробелы.

## Что property-based testing не делает автоматически

Это не магия и не просто random testing.

Нужны:
- адекватные стратегии генерации входов;
- чёткие свойства;
- понимание, где техника уместна, а где нет.

Если свойство туманное, инструмент только создаст шум.

## Где подходит плохо

- тяжёлые end-to-end сценарии;
- UI-flow с дорогим окружением;
- случаи, где expected result трудно формализовать;
- сценарии, где главный риск в интеграции, а не в чистой логике.

## Частые ошибки

- вместо свойства писать просто ещё один пример;
- выбирать слишком расплывчатый invariant;
- применять подход там, где oracle не формализуется;
- считать, что property-based testing заменяет обычные example-based checks.

## Что важно перед практикой

Перед `practice.py` ты должен понимать:
1. property-based testing проверяет инварианты, а не отдельные кейсы;
2. техника сильнее всего на чистой логике и данных;
3. хороший property-test начинается с хорошей формулировки свойства.

## Что делать дальше

1. Открой `examples.py` и посмотри, как свойства отличаются от обычных кейсов.
2. Затем переходи к `practice.py`.
3. В каждом задании сначала формулируй invariant словами, а потом уже думай о генерации входов.
