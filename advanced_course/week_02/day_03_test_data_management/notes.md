# Test Data Engineering, День 3 — Test data management

## Когда это нужно

Пока тестов мало, данные можно собирать прямо в тесте. Когда suite растёт, данные становятся отдельной инженерной задачей.

Test data management нужен, чтобы понимать:
- откуда берутся тестовые данные;
- кто ими владеет;
- как они изолируются между сценариями;
- как не получить нестабильность из-за общих данных.

## Как об этом думать

Хороший mental model: тестовые данные — это часть тестовой инфраструктуры, а не случайный побочный материал.

Нужно осознанно выбирать подход:
- данные создаются на лету;
- используются seed datasets;
- есть выделенные test fixtures;
- данные очищаются после теста или поднимаются заново изолированно.

## Какие проблемы здесь самые частые

- shared state между тестами;
- устаревшие seed-наборы;
- данные, которые подходят только под один сценарий;
- тесты, зависящие от порядка запуска.

## Что важно practically

Хорошее управление данными даёт:
- предсказуемость;
- повторяемость прогона;
- меньше flaky behavior;
- понятный источник truth для тестового окружения.

## Частые ошибки

- не различать данные для smoke и для тяжёлых интеграционных сценариев;
- хранить слишком много неиспользуемых seeds;
- использовать production-like данные без sanitation;
- не фиксировать стратегию очистки и пересоздания данных.

## Что важно перед практикой

Перед `practice.py` ты должен понимать:
1. тестовые данные требуют отдельной стратегии;
2. shared state — один из главных источников нестабильности;
3. хороший подход к данным снижает стоимость сопровождения suite.

## Что делать дальше

1. Открой `examples.py` и посмотри, как разные источники данных влияют на тесты.
2. Затем переходи к `practice.py`.
3. В каждом задании сначала определяй, какие данные должны быть одноразовыми, а какие можно переиспользовать.
