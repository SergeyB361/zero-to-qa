# API: reliability и integration, День 5 — API test architecture

## Когда это нужно

Когда API-suite растёт, raw requests, setup, assertions и data builders нельзя держать вперемешку. Без архитектуры тестовый код начинает дорожать быстрее самого продукта.

## Как об этом думать

Хороший mental model: API test framework — это слоистая система, где каждый слой отвечает на свой вопрос.

Типичное разделение:
- `client` или transport layer — как отправить запрос;
- data builders / fixtures — какие данные нужны;
- assertion helpers — что именно проверяется;
- tests — какой бизнес-сценарий происходит.

Сильный тест сверху вниз должен читаться как сценарий, а не как технический протокол HTTP.

## Что хорошая архитектура даёт practically

- уменьшает дублирование запросов;
- скрывает transport details;
- упрощает работу с auth/config/data setup;
- снижает стоимость изменения endpoint-ов и payload-ов.

## Как понять, что архитектура плохая

Плохие признаки:
- URL и headers размазаны по тестам;
- assertions смешаны с transport-кодом;
- один giant base-класс делает всё;
- тест читается как набор технических вызовов, а не как сценарий.

## Частые ошибки

- строить слишком умный framework ради самого framework;
- прятать бизнес-смысл глубоко в helper-ах;
- смешивать setup, action и verification в одном слое;
- переусложнять архитектуру раньше времени.

## Что важно перед практикой

Перед `practice.py` ты должен понимать:
1. test code тоже требует архитектуры;
2. слои transport, data и assertions должны быть разделены;
3. архитектура должна уменьшать стоимость изменений, а не добавлять ceremony.

## Что делать дальше

1. Открой `examples.py` и посмотри, как один и тот же сценарий читается при хорошем разделении слоёв.
2. Затем переходи к `practice.py`.
3. В каждом задании сначала решай, какой код должен скрывать механику, а какой должен оставаться в тесте как domain signal.
