# Test Design и Requirements Engineering, День 3 — State machines

## Когда это нужно

Если поведение системы зависит от текущего состояния сущности, обычного списка кейсов уже мало. Важны не только действия, но и разрешённые переходы между состояниями.

Именно здесь полезны state machines.

## Как об этом думать

Хороший mental model: state model описывает:
- какие состояния существуют;
- какие события или действия переводят сущность между ними;
- какие переходы разрешены;
- какие переходы запрещены.

То есть тест-дизайн здесь строится не вокруг одного input, а вокруг lifecycle объекта.

## Где это особенно полезно

- заказы и платежи;
- задачи и workflow;
- подписки и аккаунты;
- статусные API и UI flows;
- любые процессы с lifecycle rules.

## Что это даёт QA practically

- помогает не забыть forbidden transitions;
- делает workflow explainable;
- снижает риск хаотичных stateful tests;
- даёт основу для lifecycle coverage и negative cases.

## Частые ошибки

- описывать только happy path transitions;
- не фиксировать запрещённые переходы;
- путать state и action;
- строить state model слишком крупно, смешивая несколько независимых процессов.

## Что важно перед практикой

Перед `practice.py` ты должен понимать:
1. state machine — это модель поведения сущности во времени;
2. нужны и allowed, и forbidden transitions;
3. хороший state model помогает строить более сильные lifecycle tests.

## Что делать дальше

1. Открой `examples.py` и посмотри, как workflow переводится в набор переходов.
2. Затем переходи к `practice.py`.
3. В каждом задании сначала перечисляй состояния, а потом действия, которые могут их менять.
