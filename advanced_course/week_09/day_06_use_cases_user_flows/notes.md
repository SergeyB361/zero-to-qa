# Test Design и Requirements Engineering, День 6 — Use cases и user flows

## Когда это нужно

Не все требования удобно раскладывать через таблицы условий или state models. Часть поведения лучше описывать как сценарии пользователя или системные use cases.

Это особенно важно там, где тестовый смысл рождается из последовательности шагов и целей пользователя.

## Как об этом думать

Хороший mental model:
- use case отвечает на вопрос “какую цель пользователь или актор достигает через систему”;
- user flow отвечает на вопрос “какой путь он проходит до результата”.

То есть эти артефакты помогают смотреть на систему сверху, а не только через отдельные поля и статусы.

## Что они дают QA practically

- помогают увидеть пропущенные шаги и ветвления;
- связывают требования с реальным пользовательским поведением;
- подсказывают сценарии для UI и end-to-end уровней;
- хорошо работают вместе с risk analysis и state models.

## Где ошибаются чаще всего

- описывают flow слишком общо и декоративно;
- не выделяют цель пользователя;
- теряют альтернативные и негативные пути;
- смешивают один flow с несколькими независимыми use cases.

## Что важно перед практикой

Перед `practice.py` ты должен понимать:
1. use case и user flow дают пользовательский взгляд на поведение системы;
2. они полезны там, где важна последовательность шагов и достижение цели;
3. сильный flow должен помогать строить тесты, а не быть просто красивой схемой.

## Что делать дальше

1. Открой `examples.py` и посмотри, как один requirement переводится в пользовательский путь.
2. Затем переходи к `practice.py`.
3. В каждом задании сначала отвечай, какую цель пользователь пытается достигнуть, а потом описывай его путь.
