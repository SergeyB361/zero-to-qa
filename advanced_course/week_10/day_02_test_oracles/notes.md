# Quality Engineering и системное мышление, День 2 — Test oracles

## Когда это нужно

Любой тест упирается в один вопрос: как понять, что результат правильный.

Если на этот вопрос нет ясного ответа, тест становится слабым, спорным или вовсе бессмысленным. Именно это и решает понятие test oracle.

## Как об этом думать

Oracle — это источник истины для expected result.

Хороший mental model: oracle — не “мне кажется, так правильно”, а основание, по которому результат можно защитить перед другим инженером.

Источниками oracle могут быть:
- формальные требования;
- бизнес-правила;
- API contract;
- доменная логика;
- устойчивое предыдущее состояние системы;
- ограничения UX или compliance.

## Почему это важно

Слабый oracle делает тест опасным:
- тест может проверять не то;
- current implementation может быть ошибочно принята за правильное поведение;
- expected result становится интуитивным, а не доказуемым.

Хороший oracle делает проверку инженерной, а не вкусовой.

## Какие ситуации особенно сложны

Oracle особенно важен там, где:
- много derived data;
- сложные бизнес-правила;
- поведение зависит от статуса, роли, времени или внешних факторов;
- UI и API могут давать разную картину одной сущности.

## Частые ошибки

- опираться только на интуицию;
- путать текущую реализацию с правильным поведением;
- не фиксировать, откуда взят expected result;
- считать, что один oracle автоматически покрывает всю систему.

## Что важно перед практикой

Перед `practice.py` ты должен понимать:
1. любой хороший тест должен иметь защищаемый oracle;
2. oracle может приходить из нескольких источников сразу;
3. чем слабее oracle, тем выше риск ложных выводов о качестве.

## Что делать дальше

1. Открой `examples.py` и посмотри, как один и тот же сценарий может опираться на разные источники oracle.
2. Затем переходи к `practice.py`.
3. В каждом задании сначала отвечай на вопрос: на каком основании я считаю этот expected result правильным.
