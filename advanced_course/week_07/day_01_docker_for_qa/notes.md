# Infrastructure for QA, День 1 — Docker for QA

## Когда это нужно

Как только тесты зависят от конкретной версии базы, mock-сервиса, браузера или фонового приложения, локальная машина начинает мешать воспроизводимости.

Именно здесь Docker даёт практическую пользу:
- окружение можно описать как код;
- одинаковую среду можно поднять у любого инженера;
- тесты перестают зависеть от случайных локальных настроек.

## Как об этом думать

Контейнер — это не “маленькая виртуалка”, а изолированный процесс с заранее описанным окружением.

Хороший mental model:
1. `image` — это шаблон среды;
2. `container` — запущенный экземпляр этого шаблона;
3. `volume` — способ хранить данные вне жизненного цикла контейнера;
4. `port mapping` — способ связать процесс внутри контейнера с хостом.

Для QA Docker полезен не сам по себе, а как инструмент управления зависимостями тестового окружения.

## Базовый workflow

Обычно цикл выглядит так:
1. выбрать или собрать `image`;
2. запустить `container`;
3. передать нужные переменные окружения;
4. дождаться готовности сервиса;
5. выполнить тесты;
6. остановить и удалить временное окружение.

То есть Docker решает задачу “как стабильно поднять зависимые сервисы рядом с тестами”.

## Где это полезно QA practically

- локальный запуск API + DB + mock service;
- воспроизводимые integration-тесты;
- запуск временной БД для smoke/regression;
- подготовка CI-окружения так же, как локального.

## Где Docker не магия

Docker не заменяет понимание системы.

Он не решает автоматически:
- плохую конфигурацию приложения;
- неверные тестовые данные;
- race conditions;
- медленные и нестабильные тесты.

Он только делает среду более предсказуемой.

## Частые ошибки

- считать Docker заменой архитектурного понимания окружения;
- собирать один огромный образ со всем подряд;
- хранить секреты прямо в `Dockerfile` или image;
- не фиксировать версии образов;
- не различать данные контейнера и данные volume.

## Что важно перед практикой

Перед `practice.py` ты должен понимать:
1. разницу между `image` и `container`;
2. зачем нужны `ports`, `env` и `volumes`;
3. почему Docker особенно полезен для воспроизводимого test env.

## Что делать дальше

1. Открой `examples.py` и посмотри, как описывается базовое контейнерное окружение.
2. Затем переходи к `practice.py`.
3. В каждом задании сначала формулируй, какой именно кусок окружения ты хочешь стабилизировать с помощью Docker.
