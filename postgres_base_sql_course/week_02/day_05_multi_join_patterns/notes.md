# Multi-join patterns

## Когда это нужно
После первых `JOIN` быстро появляются задачи, где одной связи уже мало. Например:
- задача -> проект -> владелец проекта;
- test run -> test case -> исполнитель;
- defect -> task -> assignee.

Это уже multi-join pattern: один запрос соединяет несколько таблиц по цепочке.

## Как об этом думать
Не надо писать длинный запрос сразу. Сначала разложи его как граф связей:
1. с какой таблицы начинаешь;
2. какую таблицу добавляешь первой;
3. какую таблицу добавляешь второй;
4. какие колонки нужны в финальном результате.

## Почему порядок важен
Обычно удобнее идти от основной сущности к связанным сущностям.

Например, если задача звучит как «покажи defect, assignee task и project name», то логика такая:
- начинаем с `defects`;
- соединяем `tasks`;
- затем `projects`;
- при необходимости соединяем `users`.

## Как не потеряться в колонках
В multi-join без alias быстро становится нечитаемо. Поэтому полезно сразу договориться:
- `d` — defects
- `t` — tasks
- `p` — projects
- `u` — users

## Частые ошибки
- терять смысл запроса после второго join;
- выбирать слишком много колонок;
- путать, откуда пришла каждая колонка;
- соединять таблицы в неправильном порядке просто «потому что так получилось».

## Что нужно понимать перед практикой
Перед `practice.sql` ты должен понимать:
1. как разложить multi-join на последовательность связей;
2. почему alias здесь обязательны практически всегда;
3. как выбирать только нужные колонки из нескольких таблиц.
