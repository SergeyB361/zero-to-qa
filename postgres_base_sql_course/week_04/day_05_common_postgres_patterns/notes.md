# Common Postgres patterns

## Когда это нужно
На базовом уровне уже полезно увидеть несколько Postgres-паттернов, которые часто встречаются в реальных отчётах и диагностических запросах.

В этом дне фокус на трёх инструментах:
- `FILTER`
- `DISTINCT ON`
- `STRING_AGG`

## FILTER
`FILTER` позволяет считать несколько агрегатов с разными условиями в одном запросе.

Пример:
```sql
COUNT(*) FILTER (WHERE status = 'passed')
```

Это удобнее, чем писать несколько отдельных подзапросов для одного summary.

## DISTINCT ON
`DISTINCT ON` — Postgres-specific способ взять по одной строке на группу.

Типовой вопрос: «какой последний run был у каждого executor?»

Ключевая идея:
- `DISTINCT ON` задаёт группу;
- `ORDER BY` определяет, какая строка внутри группы останется.

## STRING_AGG
`STRING_AGG` собирает значения нескольких строк в одну строку.

Это удобно для компактного отчёта по группе, например:
- заголовки дефектов по severity;
- имена пользователей по команде;
- список статусов внутри одной группы.

## Как об этом думать
- `FILTER` — несколько условных счётчиков в одной строке.
- `DISTINCT ON` — выбрать «лучшую» или «последнюю» строку на группу.
- `STRING_AGG` — превратить несколько строк в одно текстовое summary.

## Почему это полезно уже в базе
Это ещё не тяжёлый advanced SQL, но это уже честные Postgres-инструменты, которые реально делают рабочие запросы компактнее и сильнее.

## Типичные ошибки
- использовать `DISTINCT ON` без осмысленного `ORDER BY`;
- путать `FILTER` с обычным `WHERE`;
- забывать указывать порядок внутри `STRING_AGG`, если важен стабильный вывод.

## Что нужно понимать перед практикой
Перед `practice.sql` ты должен понимать:
1. зачем нужен `FILTER`;
2. как работает `DISTINCT ON`;
3. когда использовать `STRING_AGG`.
