# Практика на SQL performance

## Зачем это нужно
Этот день нужен, чтобы соединить индексы, explain и переписывание запросов в один рабочий performance-подход.

## Ключевые идеи
- гипотеза -> план -> изменение -> повторный план
- не оптимизировать вслепую

## Практический фокус
Сначала измерь или хотя бы посмотри план. Потом меняй индекс, структуру запроса или порядок фильтрации.

## Типичные ошибки
- создавать индексы без чтения плана
- оптимизировать SQL, который и так не является bottleneck

## Практика
В `practice.sql` напиши запросы:
- `orders_plan_before_after` - Верни True, если план запроса по `/orders` меняется после индекса.
- `top_slow_endpoints` - Верни endpoint, отсортированные по средней latency.
- `failed_runs_index_usage` - Верни текст плана для failed runs после индекса.

## Что дальше
Сначала выполни `examples.sql`, затем доведи запросы из `practice.sql` до expected-результатов.
