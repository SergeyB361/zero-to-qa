# Индексы: база

## Когда это нужно

Пока таблица маленькая, запросы часто работают быстро даже без индексов. Проблема начинается, когда строк становится много: фильтрация и `JOIN` начинают читать слишком большой объём данных.

Индекс нужен, когда база должна находить строки не перебором всей таблицы, а более целевым способом.

Типичные сигналы:

- частый поиск по `user_id`, `email`, `status`, `created_at`;
- `JOIN` по внешнему ключу;
- сортировка по колонке, которую часто запрашивают.

## Как об этом думать

Хороший mental model: индекс — это вспомогательная структура рядом с таблицей, которая помогает быстрее найти нужные строки.

То есть база читает не всю таблицу целиком, а сначала смотрит в индекс, а уже потом идёт к нужным строкам.

Но у индекса есть цена:

- он занимает место;
- его нужно обновлять при `INSERT`, `UPDATE`, `DELETE`;
- лишние индексы замедляют запись и усложняют сопровождение.

## Базовый синтаксис

```sql
CREATE INDEX idx_tasks_status
ON tasks(status);
```

Читать это нужно так:

1. создать индекс с именем `idx_tasks_status`;
2. индекс строится для таблицы `tasks`;
3. внутри индекса ключом будет колонка `status`.

Часто встречается и композитный индекс:

```sql
CREATE INDEX idx_tasks_project_status
ON tasks(project_id, status);
```

Такой индекс полезен, если запросы обычно фильтруют сначала по `project_id`, а потом по `status`.

## Где индексы помогают чаще всего

1. В `WHERE`

```sql
SELECT *
FROM tasks
WHERE project_id = 10;
```

2. В `JOIN`

```sql
SELECT t.id, u.name
FROM tasks AS t
JOIN users AS u ON t.assignee_id = u.id;
```

3. В некоторых `ORDER BY`, если порядок совпадает с индексом.

## Где индексы не решают всё

Индекс не делает любой запрос быстрым автоматически.

Он может не помочь, если:

- фильтр слишком невыборочный;
- запрос использует выражение, которое ломает использование индекса;
- условие написано неудачно;
- индекс создан не по тем колонкам.

## Частые ошибки

- создавать индекс “на всякий случай”;
- индексировать почти каждую колонку подряд;
- не учитывать порядок колонок в композитном индексе;
- думать, что индекс всегда ускоряет и чтение, и запись одновременно.

## Что важно перед практикой

Перед `practice.sql` ты должен понимать:

1. индекс нужен не для красоты, а для ускорения частых сценариев доступа;
2. индекс помогает в поиске, `JOIN` и иногда сортировке;
3. у индексов есть цена, поэтому их нельзя плодить без причины.

## Что делать дальше

1. Выполни `examples.sql` и посмотри, какие индексы создаются.
2. Затем переходи к `practice.sql`.
3. В каждом задании сначала сформулируй, какой запрос ты хочешь ускорить, и только потом решай, нужен ли индекс.
