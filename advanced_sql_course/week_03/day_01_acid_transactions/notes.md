# ACID и транзакции

## Когда это нужно

Как только одна бизнес-операция затрагивает несколько изменений данных, появляется риск получить полусделанное состояние.

Например:

- деньги списались, но запись о переводе не создалась;
- заказ создался, а его позиции — нет;
- статус поменялся только в одной из связанных таблиц.

Транзакция нужна, чтобы такие изменения рассматривались как единое целое.

## Как об этом думать

Хороший mental model: транзакция — это пакет изменений, который либо фиксируется полностью, либо откатывается полностью.

ACID — это не набор букв ради собеседования, а набор свойств, которые делают такой пакет надёжным:

- `Atomicity` — всё или ничего;
- `Consistency` — данные после транзакции должны остаться корректными;
- `Isolation` — параллельные операции не должны ломать друг другу смысл;
- `Durability` — после фиксации результат должен сохраниться.

## Базовый синтаксис

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

Читать это нужно так:

1. начать транзакцию;
2. выполнить все изменения как одну операцию;
3. зафиксировать результат только в конце.

Если посередине что-то пошло не так, вместо `COMMIT` нужен `ROLLBACK`.

## Где это критично

- переводы и любые финансовые сценарии;
- создание связанных сущностей;
- массовые обновления;
- миграции и backfill-операции.

## Частые ошибки

- думать, что каждый `UPDATE` безопасен сам по себе;
- начинать транзакцию и забывать её завершить;
- обсуждать ACID абстрактно, без конкретных сценариев;
- путать “транзакция есть” и “логика операции действительно корректна”.

## Что важно перед практикой

Перед `practice.sql` ты должен понимать:

1. зачем несколько изменений объединяют в транзакцию;
2. что такое `BEGIN`, `COMMIT`, `ROLLBACK`;
3. почему ACID — это practical модель надёжности, а не просто теория.
