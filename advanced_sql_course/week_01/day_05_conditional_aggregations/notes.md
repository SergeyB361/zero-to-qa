# Conditional aggregations

## Когда это нужно
Обычная агрегация считает всё подряд. Но в реальных отчётах часто нужны метрики только для части строк:
- сколько `failed` внутри группы;
- сколько `open` дефектов по severity;
- сколько успешных API-check внутри endpoint.

Для этого используют условные агрегации.

## Как об этом думать
Сначала есть группа строк.

Потом внутри неё ты задаёшь вопрос:
- какие строки считать в одну метрику;
- какие в другую;
- какие вообще игнорировать.

То есть логика становится двухслойной:
1. разбить строки на группы;
2. внутри группы посчитать разные метрики по условиям.

## Базовый паттерн
Самый частый паттерн выглядит так:

```sql
SUM(CASE WHEN status = 'failed' THEN 1 ELSE 0 END)
```

Это значит:
- если строка `failed`, дай ей вес 1;
- иначе 0;
- потом просуммируй.

В результате получишь количество failed-строк внутри группы.

## Где это особенно полезно
- dashboard-метрики;
- отчёты “open vs closed”;
- сравнение passed/failed/skipped;
- аналитика по severity, endpoint, area, release.

## Почему это лучше, чем много отдельных запросов
Условная агрегация позволяет собрать несколько метрик в одном SQL.

Это полезно, когда нужен компактный отчёт, а не пачка разрозненных выборок.

## Частые ошибки
- забывать `ELSE 0` и получать `NULL`-логические эффекты;
- путать условную агрегацию с обычной фильтрацией `WHERE`;
- считать, что `WHERE` и `CASE` внутри агрегации взаимозаменяемы;
- перегружать один запрос десятками колонок, теряя читаемость.

## Что важно понять перед практикой
1. `WHERE` отрезает строки целиком до агрегации.
2. `CASE` внутри `SUM/COUNT` считает условие внутри уже выбранной группы.
3. Одним запросом можно получить несколько бизнес-метрик по одним и тем же строкам.
