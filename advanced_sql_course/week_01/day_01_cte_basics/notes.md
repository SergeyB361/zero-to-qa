# CTE: база

## Когда это нужно
CTE нужен, когда запрос логически состоит из нескольких шагов, и эти шаги хочется явно назвать.

Обычный сигнал, что CTE уместен:
- сначала нужно собрать промежуточный набор строк;
- потом агрегировать его;
- потом ещё раз использовать этот результат в основном запросе.

Без CTE такой SQL быстро превращается в тяжёлый вложенный подзапрос, который трудно читать и отлаживать.

## Как об этом думать
CTE через `WITH` позволяет вынести промежуточный шаг в именованный блок.

То есть ты пишешь не просто “один большой запрос”, а последовательность этапов:
1. собрать нужные строки;
2. посчитать промежуточные метрики;
3. взять итоговый результат.

Хороший mental model: CTE — это как аккуратно названный временный результат внутри одного SQL-запроса.

## Базовый синтаксис
```sql
WITH failed_runs AS (
    SELECT case_id
    FROM test_runs
    WHERE status = 'failed'
)
SELECT case_id, COUNT(*)
FROM failed_runs
GROUP BY case_id;
```

Читать это нужно так:
- сначала создай именованный набор `failed_runs`;
- потом используй его как обычную таблицу в основном запросе.

## Что CTE даёт practically
- улучшает читаемость длинного SQL;
- делает промежуточную логику явной;
- помогает отлаживать сложные отчёты по шагам;
- упрощает обсуждение запроса с другими разработчиками.

## Когда CTE лучше подзапроса
CTE особенно хорош, если:
- промежуточный шаг важен по смыслу;
- у шага есть хорошее имя;
- запрос читается сверху вниз как сценарий;
- один и тот же промежуточный результат нужен больше одного раза.

Если подзапрос короткий и тривиальный, CTE может и не понадобиться.

## Частые ошибки
- делать `WITH` просто ради моды;
- называть CTE бессмысленно: `tmp1`, `x`, `data2`;
- разбивать простой запрос на 5 лишних блоков;
- терять бизнес-смысл промежуточного шага.

## Что важно перед практикой
Перед `practice.sql` ты должен понимать:
1. что `WITH` создаёт именованный промежуточный результат;
2. как читать запрос сверху вниз по этапам;
3. почему хороший CTE делает SQL понятнее, а не сложнее.

## Что делать дальше
1. Выполни `examples.sql` и посмотри, как один запрос раскладывается на этапы.
2. Затем переходи к `practice.sql`.
3. В каждом задании сначала придумай имя промежуточному шагу, а потом уже пиши SQL.
