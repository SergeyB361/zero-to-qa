# SQL для backend и API-анализа

## Зачем это нужно
Когда у backend-команды проблема в проде или деградация на стенде, им обычно не нужен "красивый SQL-отчёт". Им нужен быстрый ответ на инженерный вопрос:

- какие endpoint стали медленнее;
- после какого релиза выросло число ошибок;
- есть ли связь между API-checks и критичными дефектами.

Именно для этого SQL и полезен в backend/API-анализе.

## Как думать о таких запросах
Здесь SQL работает как инструмент расследования. Ты не строишь абстрактную витрину данных, а отвечаешь на конкретный operational question.

Хороший запрос в таком контексте:
- отвечает на один вопрос;
- использует понятную агрегацию;
- помогает принять следующее действие;
- читается другим инженером без долгой расшифровки.

## Какие вопросы чаще всего решают
На практическом уровне чаще всего нужны такие срезы:

- средняя или максимальная latency по endpoint;
- распределение ошибок по релизам;
- связь между релизом, ошибками и дефектами;
- участки системы, где деградация повторяется чаще всего.

Это уже не "SQL ради SQL", а часть инженерной диагностики.

## Где тут роль QA
QA или automation engineer часто участвует в таких запросах, когда нужно:

- быстро подтвердить гипотезу по инциденту;
- сопоставить падения API-checks с релизом;
- проверить, не связаны ли backend-ошибки с уже известными defect-ами;
- дать команде не сырые таблицы, а понятный вывод по данным.

## Частые ошибки
- писать запрос, который выглядит умно, но не отвечает на вопрос команды;
- смешивать несколько разных метрик в один тяжёлый отчёт;
- не фильтровать данные по нужному релизу, статусу или периоду;
- возвращать результат, который неудобно читать во время расследования.

## Практика
В `practice.py` ты решаешь три типовых аналитических вопроса:

- `slow_endpoints` - какие endpoint самые медленные по средней latency;
- `error_rate_by_release` - в каких релизах больше ошибок со статусом `>= 400`;
- `critical_defects_by_release` - какие релизы связаны с critical defect.

## Что должно остаться после урока
После этого урока ты должен уметь:

1. переводить инженерный вопрос в SQL-запрос;
2. выбирать нужную агрегацию вместо "общего красивого отчёта";
3. читать результат глазами человека, который расследует проблему, а не просто тренируется в SQL.
