# DB-checks в тестах

## Зачем это нужно
Ответ приложения и состояние базы решают разные задачи. API может вернуть `200 OK`, но в таблице окажется неверный статус, не та связь или дубликат строки. DB-check нужен там, где база выступает источником истины.

## Как выглядит полезный DB-check
Нормальная проверка строится так:

1. тест делает действие через API, UI или сервисный слой;
2. тест формулирует, какое состояние обязано появиться в базе;
3. SQL-запрос проверяет только это состояние;
4. результат проверяется через `assert`, а не через `print`.

Здесь важно не "сделать запрос любой ценой", а доказать конкретный факт:
- строка создана;
- значение колонки обновилось;
- количество записей не выросло лишний раз;
- связанная сущность появилась там, где должна.

## Чем DB-check отличается от просто запуска SQL
Сам SQL ещё не делает код тестом. Тест начинается там, где появляется проверка ожидания:

- `assert count == 2`
- `assert exists is True`
- `assert status == "closed"`

Если код только печатает строки и результаты запросов, это отладка, а не тест.

## Когда DB-check оправдан
- нужно подтвердить сохранение данных после API-вызова;
- нужно проверить побочный эффект, который не виден в ответе API;
- важна консистентность между несколькими таблицами;
- есть риск тихой деградации данных, которую UI не показывает.

## Когда DB-check лучше не делать
- если тот же факт уже стабильно проверяется через публичный контракт API;
- если запрос слишком жёстко привязан к внутренней схеме и не даёт ценной проверки;
- если тест начинает проверять пол-БД вместо одного инварианта.

Хороший принцип: один DB-check должен подтверждать один важный факт.

## Как писать такие проверки
Лучше иметь маленькие helper-функции:
- `scalar(...)` для `COUNT(*)` и других одиночных значений;
- `row_exists(...)` для проверки факта наличия строки;
- `assert_scalar_equals(...)` или похожий helper для читаемого сообщения об ошибке.

Тогда тест читается как сценарий, а не как набор сырых `fetchone()`.

## Частые ошибки
- писать запрос шире, чем нужно;
- сравнивать случайные данные вместо устойчивого бизнес-факта;
- забывать про `LIMIT 1`, когда нужен только факт существования;
- делать `print`, но не делать `assert`;
- смешивать setup данных и саму проверку в один нечитаемый блок.

## Что нужно уметь перед практикой
Перед `practice.py` ты должен понимать:

1. какой факт в базе проверяет тест;
2. какой минимальный SQL нужен для этой проверки;
3. почему DB-check должен заканчиваться `assert`, а не печатью результата.
