# Реалистичные SQL-запросы для QA

## Зачем нужен этот день
Отдельные темы полезны, но реальная работа почти никогда не выглядит как "чистый пример на одну конструкцию". Обычно запросы смешанные: фильтры, join, агрегаты, existence-checks, сортировка.

## Как думать о реальном запросе
Не начинай с синтаксиса. Начни с вопроса к системе.

Например:
- какие пользователи создали заказы за сегодня;
- какие тест-кейсы падали чаще двух раз;
- какие задачи открыты и не имеют исполнителя.

Если вопрос сформулирован ясно, SQL строится намного проще.

## Рабочий порядок
Полезно идти так:
1. сформулировать вопрос обычным языком;
2. определить нужные таблицы;
3. определить связь между ними;
4. выбрать форму результата: строки, группы, существование, одно число;
5. только потом писать запрос.

## Почему это важно именно QA
QA часто использует SQL не для аналитики ради аналитики, а для расследования поведения системы:
- что записалось в базу;
- почему API вернул один статус, а данные выглядят иначе;
- где потерялась связь между сущностями;
- соответствует ли фактическое состояние ожидаемому.

## Что здесь тренируется
В этот день главный навык - перевод прикладного вопроса в аккуратный SQL.

Это уже ближе к реальной работе, чем к учебным примерам.

## Частые ошибки
- сразу писать сложный запрос без разбиения на смысловые шаги;
- не понимать, какие таблицы реально участвуют в ответе;
- брать слишком много колонок;
- не проверять промежуточный результат на маленькой выборке.

## Что проверить перед практикой
Перед `practice.py` ты должен быть готов:
1. описать задачу словами до SQL;
2. выбрать правильный тип запроса под смысл задачи;
3. читать SQL как отражение бизнес-вопроса, а не как набор случайных ключевых слов.
