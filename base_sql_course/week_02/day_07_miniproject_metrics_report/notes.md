# Мини-проект: Metrics Report

## Зачем этот проект
Это первая маленькая задача, где SQL используется не как набор отдельных упражнений, а как инструмент построения отчёта.

Проект заставляет собрать вместе:
- фильтрацию;
- агрегаты;
- `GROUP BY` и `HAVING`;
- `JOIN`;
- аккуратное чтение результата.

## Как к нему подходить
Не пытайся сразу писать большой финальный запрос. Это самый быстрый путь к путанице.

Правильный порядок:
1. посмотри на таблицы и пойми, что в них лежит;
2. напиши простой `SELECT` без группировок и join, чтобы увидеть данные;
3. отдельно проверь фильтры;
4. отдельно проверь агрегацию;
5. потом собирай итоговый отчёт.

## Что здесь реально тренируется
Главный навык проекта - не синтаксис, а умение превратить бизнес-вопрос в SQL.

Например, вопрос "сколько failed runs было у каждого test case" нужно разложить на части:
- какие таблицы участвуют;
- как они связаны;
- какие строки брать;
- по чему группировать;
- что считать итогом.

## На что смотреть в готовом ответе
Хороший запрос здесь:
- читается слева направо;
- использует понятные alias;
- не смешивает в кучу 10 колонок без причины;
- даёт предсказуемый результат на маленьком наборе данных.

## На чём обычно ломаются
- начинают с слишком большого запроса;
- не проверяют промежуточные шаги;
- не понимают форму результата после `GROUP BY`;
- используют `LEFT JOIN`, когда нужен `INNER JOIN`, и наоборот.

## Что проверить перед реализацией
Перед `spec.md` и кодом ты должен понимать:
1. какие SQL-конструкции из недели здесь комбинируются;
2. как проверять промежуточный результат маленькими запросами;
3. почему хороший отчёт начинается с ясной логики, а не с длинного текста SQL.
