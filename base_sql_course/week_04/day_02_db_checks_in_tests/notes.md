# DB-checks в тестах

## Зачем это нужно
Иногда UI или API отвечает корректно, но данные в базе оказались не теми. Поэтому проверки только на уровне ответа не всегда достаточно.

## Как думать о DB-check
DB-check - это не отдельный вид магии, а дополнительная проверка источника истины.

Ты делаешь действие через приложение, а потом проверяешь, что в базе произошло именно то изменение, которое ожидалось:
- создалась строка;
- статус обновился;
- значение сохранилось правильно;
- лишние строки не появились.

## Когда DB-check оправдан
Он полезен, когда база - важная часть контракта системы.

Например:
- после создания заказа должна появиться запись;
- после деактивации пользователя флаг `is_active` должен стать `0`;
- после запуска теста должен создаться run в таблице `test_runs`.

## Когда DB-check вреден
Не стоит тащить SQL в каждый тест без причины. Иначе тесты станут слишком жёстко привязаны к внутренней схеме и будут ломаться при любом рефакторинге.

Хороший принцип: DB-check нужен там, где он реально подтверждает важное состояние системы.

## Как строить такую проверку
Нормальный порядок:
1. выполни действие через приложение или тестовый код;
2. сформулируй, что именно должно измениться в базе;
3. напиши минимальный запрос, который это подтверждает;
4. проверь не только наличие строки, но и правильность ключевых значений.

## Частые ошибки
- проверять слишком много колонок без необходимости;
- писать хрупкие запросы, завязанные на случайные детали схемы;
- делать DB-check там, где достаточно API-ответа;
- не очищать данные после теста.

## Что проверить перед практикой
Перед `practice.py` ты должен понимать:
1. зачем DB-check нужен поверх обычной проверки теста;
2. какой SQL должен быть минимально достаточным;
3. почему DB-check - это точечный инструмент, а не обязательная часть любого теста.
