# Финальный мини-проект: DB Checks Toolkit

## Зачем этот проект
Финальный проект нужен, чтобы SQL перестал быть учебным изолированным навыком и превратился в часть инженерного инструмента.

Здесь ты уже не просто пишешь отдельные запросы, а собираешь маленький toolkit, который похож на реальную вспомогательную утилиту QA.

## Что здесь объединяется
Проект сводит вместе несколько навыков:
- понимание схемы данных;
- написание осмысленных запросов;
- использование SQLite из Python;
- DB-checks;
- подготовку данных и простую диагностику.

## Как к нему подходить
Не пытайся сразу сделать всё красиво и универсально. Сначала собери минимально рабочий вариант.

Хороший порядок:
1. понять, какие проверки toolkit должен уметь делать;
2. определить, какие SQL-запросы для этого нужны;
3. вынести их в понятные функции;
4. проверить toolkit на небольшом демо-наборе данных.

## Что считается хорошим результатом
Для базового курса хороший финальный проект:
- читается без мучений;
- использует небольшие и понятные SQL-запросы;
- возвращает предсказуемый результат;
- показывает, как SQL помогает проверять состояние системы.

Это не соревнование в количестве строк. Здесь важнее ясность и прикладная ценность.

## На чём обычно ломаются
- пытаются написать "универсальный движок" вместо маленького понятного инструмента;
- смешивают создание данных, SQL и вывод так, что код трудно читать;
- не проверяют toolkit на маленьких примерах;
- не могут объяснить, какую именно проверку делает функция.

## Что проверить перед реализацией
Перед `spec.md` и стартовым файлом ты должен понимать:
1. какие проверки toolkit должен уметь выполнять;
2. как SQL встроится в Python-код;
3. почему хороший финальный проект показывает прикладное мышление, а не просто длинный файл.
