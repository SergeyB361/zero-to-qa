# FastAPI Basics, Week 2 Day 2 — service layer и in-memory repository

## Зачем разделять route, service и repository
Если route-функция сама:
- читает вход;
- принимает бизнес-решение;
- ищет данные;
- меняет storage;
- собирает ответ,

то она очень быстро становится перегруженной.

Поэтому даже на простом проекте полезно разделять слои.

## Простая модель разделения
### Route layer
Отвечает за HTTP:
- какой endpoint вызван;
- какие входные данные пришли;
- какой status code вернуть.

### Service layer
Отвечает за поведение системы:
- что делать при создании сущности;
- какие правила применить;
- как изменять состояние.

### Repository layer
Отвечает за доступ к данным:
- list;
- get by id;
- create;
- delete.

## Почему даже in-memory repository полезен
Даже если storage пока просто список в памяти, repository всё равно полезен.

Он даёт:
- единое место доступа к данным;
- меньше дублирования;
- более понятные границы кода;
- более простой переход к настоящему persistence слою позже.

То есть это не “псевдоархитектура”, а тренировка нормального разделения ответственности.

## Что service layer даёт на практике
Service layer полезен тем, что route перестаёт знать детали работы с данными.

Route не должен решать:
- как формируется новая сущность;
- где лежит storage;
- какие правила применяются при изменении статуса;
- как обрабатываются доменные ограничения.

Route лучше оставить thin and readable.

## Где проходит разумная граница
Не нужно строить enterprise-архитектуру на 20 классов.

На этом уровне достаточно, чтобы было понятно:
- где HTTP;
- где логика;
- где данные.

То есть цель не в количестве слоёв, а в ясной ответственности.

## Где ошибаются чаще всего
- Пихают SQL/поиск/валидацию прямо в route.
- Создают слишком много абстракций без реальной пользы.
- Делают service и repository формально, но route всё равно знает внутренности storage.
- Путают “читаемая архитектура” и “максимально много файлов”.

## Что нужно вынести из урока
Перед практикой ты должен понимать:
1. почему route не должен быть контейнером для всей логики;
2. зачем нужен service layer;
3. чем полезен даже простой in-memory repository.
