# FastAPI Basics, Week 2 Day 1 — APIRouter и структура проекта

## Почему одного `main.py` быстро становится мало
В самом начале один файл удобен. Но как только в API появляются разные зоны ответственности, всё начинает смешиваться:
- users;
- tasks;
- reports;
- auth;
- health endpoints.

Если всё лежит в одном `main.py`, код быстро становится тяжёлым для чтения.

## Что решает `APIRouter`
`APIRouter` позволяет группировать связанные endpoints.

Например:
- router для `/users`;
- router для `/projects`;
- router для `/tasks`.

Потом приложение собирается из этих частей через `include_router()`.

То есть идея простая: не один большой API-файл, а несколько локально связанных модулей.

## Как это выглядит по слоям
Минимально полезная структура может быть такой:

```text
app/
  main.py
  routers/
    users.py
    tasks.py
  schemas.py
  services.py
```

Что здесь важно:
- `main.py` собирает приложение;
- `routers/` описывает HTTP-вход;
- схемы и сервисы лежат отдельно.

Даже если структура ещё маленькая, это уже дисциплинирует код.

## Что `APIRouter` не делает
`APIRouter` не решает архитектуру за тебя.

Он не заменяет:
- service layer;
- repository layer;
- доменную модель.

Он только помогает разложить HTTP-часть по модулям.

## Когда уже пора дробить приложение
Хороший сигнал, что пора использовать router-ы:
- в одном файле уже несколько ресурсных зон;
- file scroll становится слишком длинным;
- трудно быстро понять, где лежит конкретный endpoint;
- хочется отделить wiring от логики.

## Когда не стоит усложнять структуру
Если у тебя буквально 2 route-а и один экспериментальный файл, дробить приложение на 12 модулей рано.

Хорошая архитектура — это не максимальное число файлов, а разумная читаемость.

## Где ошибаются чаще всего
- Держат всё в одном файле слишком долго.
- Либо, наоборот, слишком рано разбивают код на множество пустых модулей.
- Путают router layer и business logic layer.
- Начинают думать, что `APIRouter` уже сам по себе означает хорошую архитектуру. Не означает.

## Что нужно вынести из урока
Перед практикой ты должен понимать:
1. зачем нужен `APIRouter`;
2. какую задачу решает структура проекта;
3. почему разбиение по модулям полезно, но не должно превращаться в бессмысленную дробность.
