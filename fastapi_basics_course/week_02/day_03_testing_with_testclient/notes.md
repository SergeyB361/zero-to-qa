# FastAPI Basics, Week 2 Day 3 — тестирование через TestClient

## Почему FastAPI нужно тестировать именно как API
Даже если endpoint написан как обычная Python-функция, реальная ценность сервиса — в HTTP-контракте.

Клиенту важно не только, что функция “логически работает”, но и:
- какой URL вызвать;
- какой method использовать;
- какой status code он получит;
- какой JSON придёт в ответе.

Поэтому тестирование FastAPI — это не только unit-level проверка функций, но и проверка API-поведения.

## Что даёт `TestClient`
`TestClient` позволяет тестировать приложение как HTTP API без подъёма внешнего сервера в отдельном процессе.

На базовом уровне это удобно, потому что ты можешь писать:
```python
client.get('/health')
client.post('/tasks', json={...})
```

И проверять результат как у настоящего HTTP-запроса.

## Что именно нужно проверять в тесте
Минимальный набор для хорошего FastAPI-теста:
- `status_code`;
- `response.json()`;
- при необходимости — форму данных и ключевые поля.

Иногда этого уже достаточно, чтобы поймать контрактную ошибку.

## Как выглядит хороший маленький тест
```python
response = client.get('/health')
assert response.status_code == 200
assert response.json() == {'status': 'ok'}
```

Это хороший пример, потому что тест проверяет:
- endpoint вообще доступен;
- код ответа корректный;
- JSON-форма ответа соответствует ожиданию.

## Чем такие тесты отличаются от unit-тестов
Unit-тест обычно проверяет чистую функцию и не думает об HTTP-слое.

Тест через `TestClient` уже ближе к integration-style проверке:
- приложение маршрутизирует запрос;
- framework обрабатывает вход;
- endpoint формирует ответ;
- тест проверяет контракт.

То есть это уже не “просто проверка функции”.

## Что не стоит делать в таком тесте
Плохая практика:
- проверять только `200` и не смотреть в body;
- делать один giant test на несколько сценариев сразу;
- проверять внутренности framework-а вместо контракта своего API.

Задача теста — не доказать, что FastAPI существует, а проверить, что твой сервис ведёт себя правильно.

## Как думать про happy path и negative path
Для FastAPI-тестов полезно сразу держать две категории сценариев:
- happy path: корректный запрос, ожидаемый успешный ответ;
- negative path: невалидный вход, отсутствие объекта, ошибка auth и т.д.

Если тестировать только happy path, API быстро начинает врать в крайних случаях.

## Где ошибаются чаще всего
- Проверяют только `status_code == 200`.
- Не сравнивают фактический JSON с ожиданием.
- Делают слишком большой тест на несколько разных сценариев.
- Путают тестирование контракта и тестирование внутренних реализационных деталей.

## Что нужно вынести из урока
Перед практикой ты должен понимать:
1. зачем нужен `TestClient`;
2. что именно должен проверять FastAPI-тест;
3. почему API-контракт нужно тестировать отдельно от чистой бизнес-логики.
