# FastAPI Basics, Week 1 Day 4 — request body и Pydantic

## Зачем нужен request body
Как только endpoint начинает принимать структурированные данные, одного URL уже недостаточно.

Например, для создания задачи тебе нужны:
- title;
- description;
- priority;
- assignee.

Передавать всё это через query string неудобно и методически слабо. Для таких случаев используют request body, обычно в формате JSON.

## Зачем здесь Pydantic
Pydantic-модель нужна, чтобы входной контракт был явным.

Вместо такого подхода:
```python
@app.post('/tasks')
def create_task(payload: dict):
    ...
```

Ты описываешь схему явно:
```python
class TaskCreate(BaseModel):
    title: str
    priority: str
    description: str | None = None
```

Это даёт сразу несколько вещей:
- читаемую схему входа;
- типы полей;
- required/optional поля;
- defaults;
- автоматическую валидацию.

## Что реально происходит в FastAPI
Когда клиент отправляет JSON, FastAPI:
1. читает тело запроса;
2. пытается собрать объект Pydantic-модели;
3. если данные подходят — передаёт уже готовый объект в route;
4. если не подходят — сам возвращает validation error.

Это сильнее, чем вручную разбирать словарь и проверять поля по месту.

## Как различать required и optional поля
Если поле объявлено без default, оно обязательное:
```python
title: str
```

Если у поля есть default или `None`, оно уже optional:
```python
description: str | None = None
```

Это важно, потому что API-контракт должен быть предсказуемым для клиента.

## Почему не стоит жить на `dict`
`dict` можно использовать в прототипе, но у него есть проблемы:
- не видно форму входных данных;
- нет явной схемы;
- валидацию приходится писать вручную;
- документация API становится слабее.

Pydantic в FastAPI — это не украшение, а базовый инженерный инструмент.

## Входная модель и выходная модель — не одно и то же
Частая ошибка новичка: использовать одну и ту же модель и на вход, и на выход без размышления.

Но на практике они часто разные.

Например:
- на вход клиент не передаёт `id`;
- на выход сервер уже возвращает `id`.

То есть `TaskCreate` и `TaskOut` могут и должны отличаться.

## Где ошибаются чаще всего
- Используют свободный `dict` там, где нужен стабильный контракт.
- Смешивают входную и выходную модель.
- Не думают, какие поля действительно обязательны.
- Пытаются засунуть в одну модель всё подряд без роли модели в API.

## Что нужно вынести из урока
Перед практикой ты должен понимать:
1. зачем request body лучше подходит для структурированных данных;
2. что именно даёт `BaseModel`;
3. почему Pydantic-модель — это часть публичного контракта API.
