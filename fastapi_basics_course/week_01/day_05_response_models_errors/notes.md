# FastAPI Basics, Week 1 Day 5 — response_model, status codes, errors

## Почему эта тема важна
API-контракт — это не только входные данные. Не менее важно, что именно сервис возвращает на выходе:
- какие поля есть в ответе;
- какой status code приходит клиенту;
- как оформляется ошибка.

Если это не зафиксировать, клиенту сложно предсказать поведение API.

## Что делает `response_model`
`response_model` задаёт форму ответа.

Пример:
```python
class UserOut(BaseModel):
    id: int
    name: str

@app.get('/users/{user_id}', response_model=UserOut)
def get_user(user_id: int):
    ...
```

Смысл здесь простой:
- endpoint должен возвращать объект, совместимый с `UserOut`;
- FastAPI валидирует и сериализует ответ;
- клиент получает более стабильный контракт.

То есть `response_model` нужен не ради красоты, а ради предсказуемого API.

## Как думать про status code
Status code — это не просто число “для галочки”. Это часть смысла ответа.

Базовые случаи, которые нужно различать:
- `200 OK` — запрос успешно обработан;
- `201 Created` — ресурс успешно создан;
- `404 Not Found` — запрошенный объект не найден;
- `400` / `422` — клиент прислал невалидные данные;
- `401` / `403` — проблема с доступом.

Если API всегда отвечает `200`, даже когда произошла ошибка, это плохой контракт.

## Как работает `HTTPException`
`HTTPException` нужен, чтобы явно завершить запрос ошибкой.

Пример:
```python
raise HTTPException(status_code=404, detail='user not found')
```

Это значит:
- route не продолжается дальше;
- FastAPI формирует HTTP-ответ с нужным кодом;
- клиент получает понятную ошибку.

## Happy path и error path
Сильный endpoint нужно проектировать сразу в двух режимах:
- что происходит, если всё хорошо;
- что происходит, если объект не найден или вход невалиден.

Если разработчик думает только про happy path, API почти всегда получается хрупким.

## Почему форма ответа должна быть стабильной
Плохая практика:
- иногда вернуть `{'user': ...}`;
- иногда вернуть `{'data': ...}`;
- иногда вернуть просто список;
- иногда вернуть вообще другую вложенность.

Клиенту от такого API больно. Он не знает, что ожидать.

Поэтому `response_model` и явные error responses помогают держать форму ответа под контролем.

## Где ошибаются чаще всего
- Возвращают разную структуру JSON из одного и того же endpoint.
- Отдают `200 OK` там, где по смыслу нужен `201` или `404`.
- Прячут ошибку в поле `detail`, но оставляют успешный status code.
- Не думают об error path заранее.

## Что нужно вынести из урока
Перед практикой ты должен понимать:
1. зачем нужен `response_model`;
2. почему status code — это часть API-контракта;
3. как `HTTPException` помогает явно оформлять ошибки.
